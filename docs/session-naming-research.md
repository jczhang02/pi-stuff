# Session naming: rules, timing and task stability

[简体中文](i18n/zh-CN/session-naming-research.md). Investigated on 2026-09-22. This is a research report, not an accepted implementation specification.

The question is how a session name can keep identifying the user's main task while the conversation moves through clarification, implementation and troubleshooting. Source inspection can establish the input, prompt, trigger and update conditions. It cannot establish actual title quality without evaluating generated names against representative conversations.

This revision replaces the earlier default-cooldown recommendation. A cooldown bounds request frequency; it does not stop a title from following the latest subtask. Conversely, a title generated once cannot drift later, but it can permanently preserve an early misunderstanding. Both failure modes matter.

## What counts as evidence

We compare persisted session/task titles and the persisted summaries used as session-list labels. Terminal-window status, compaction summaries and commit messages serve different purposes. Code-backed rows identify a version or commit. Documentation-only behavior is marked explicitly. Public issue reports are examples of observed failures, not proof that every user or current version has the defect. Independent packages are distinguished from adaptations of the same naming implementation.

No inspected external code was installed or executed and no live naming-model requests were made in this expanded survey. The earlier Pi 0.85.1 in-memory metadata probe remains valid, with its limited purpose stated below.

### What the most relevant packages actually guarantee

`pi-session-namer` is the clearest example of separating identity fields from progress. Its code compares segments and can distinguish a progress-only update from a topic update. However, the model still decides the new type/topic, and its context is latest-biased. The equality check does not prove that a changed topic is justified; `taskChanged` affects notification, not write eligibility. Progress remains part of the rendered name, so this is semantic anchoring rather than immutable title text. [Prompt and update path](https://github.com/joshua-zyy/pi-session-namer/blob/1d10dfd719438f457a29641ae05973af21e795d4/src/index.ts#L206-L315).

`patlux/pi-auto-session-name` solves a different problem: provide a useful early label, then stop automatic replacement. Its active timeout helps long first runs, while retaining opening context reduces influence from later incidental work. After compaction, the summary is an input anchor rather than the original verbatim request, so summary fidelity matters. [Excerpt construction](https://github.com/patlux/pi-auto-session-name/blob/19a83557d77638a25b065755be6779eaad901101/src/title.ts#L56-L101), [eligibility](https://github.com/patlux/pi-auto-session-name/blob/19a83557d77638a25b065755be6779eaad901101/src/index.ts#L164-L255).

`@furbyhaxx/pi-session-naming` and oh-my-pi acknowledge that some openings cannot support a meaningful name. Deferring a title or keeping an explicitly temporary placeholder is preferable to manufacturing specificity. The ten-turn retry schedule and the English filler filter are implementation choices, not evidence of an optimal clarification detector.

## Naming rules worth evaluating

The recurring useful rule is to identify the requested outcome and its object, preserving the few identifiers that make the task findable. The sources vary widely on length: four words, five words, 3-8 words, 50/80 characters. These are product choices, not an established universal standard. Chinese titles need character/display-width handling rather than an English word-count rule.

For this task, proposed examples are `Session 自动命名规则调研` and, if the scope later explicitly becomes implementation, `实现 Session 自动命名`. A tool search, lint failure or commit step should not cause names such as `修复 lint` or `提交代码` while the original naming task remains active. These examples are intended acceptance cases, not model outputs observed in this survey.

A candidate prompt should specify: main user objective; concrete object; original technical identifiers; user's language; no invented specifics; no status or incidental steps; keep a still-correct current name exactly; distinguish clarification/correction from goal replacement. Input selection and write eligibility must enforce the parts that can be enforced mechanically. A prompt alone cannot guarantee the semantic judgment.

## What prevents drift, and what does not

| Mechanism                                  | What it actually controls                               | Remaining weakness                                                                 |
| ------------------------------------------ | ------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Generate once, then freeze                 | Later messages cannot replace the title                 | A vague opener or early wrong interpretation remains frozen                        |
| Use a fixed opening conversation window    | Later implementation details do not enter naming input  | Corrections outside that window are invisible                                      |
| Keep the original request plus recent text | Preserves an explicit reference to the starting task    | Recent text can still dominate; an initial misunderstanding still needs correction |
| Tell the model to keep the current title   | Discourages unnecessary changes through prompt guidance | No structural guarantee; the model still decides whether a change is warranted     |
| Delay or repeat early naming               | Lets clarifications influence the title                 | Fixed turn counts do not establish that clarification is complete                  |
| Cooldown or every-N-turn cadence           | Bounds request frequency                                | Says nothing about whether the task identity changed                               |
| Manual-name lock and stale-write check     | Protects user intent and concurrent updates             | Does not make an automatically generated title semantically correct                |

A stable title and a correct title are separate properties. The strongest structural stability comes from limiting later writes or inputs. The hardest unresolved question is which later user messages correct or replace the main task, and which merely describe a step toward it.

## Implications for Pi Stuff

The surveyed rules should be evaluated against the maintainer's requirement: name the main requested outcome and object, with a scope constraint only when it distinguishes the task. A local debugging step, status update or work phase should not become the session's identity just because it is recent. This is our proposed evaluation criterion, not a claim that every harness implements such a model.

The evidence supports testing a bounded early naming/refinement policy against a once-only baseline. It does not justify treating ten minutes, three turns or five turns as an optimal threshold. A separate persisted core-task record has an ecosystem precedent in structured naming, but its necessity remains unproven. Compare it with the simpler alternative of retaining selected initial user instructions and explicit later corrections. If progress must be visible, give it a separate field so the stable task label does not change during ordinary phases.

Before selecting the policy, compare these conversations:

| Conversation case                                               | Desired property                                                         |
| --------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Vague opener, then an explicit target                           | The final name reflects the clarification instead of freezing the opener |
| Research, implementation and tests for the same feature         | Phase changes preserve task identity                                     |
| A temporary lint, environment or dependency blocker             | The title does not become the name of the blocking subtask               |
| The user corrects the misunderstood target                      | A wrong initial name can be corrected                                    |
| The user explicitly replaces the main goal                      | The policy can distinguish replacement from a side request               |
| Long initial logs or injected context before the actual request | Input truncation does not discard the task                               |
| Chinese prose with English technical identifiers                | The title preserves meaning and recognizable identifiers                 |
| Manual rename while generation is pending                       | The generated result cannot overwrite the manual choice                  |

Measure main-goal match, temporary-step contamination, correction after clarification and unnecessary title changes separately. Track naming requests and latency as operational costs. These are proposed evaluation cases, not completed experiments or fabricated scores.

Its configuration rejects unknown fields, so old `sessionNaming` settings cannot simply be copied into the current version. Settlement alone is neither success nor direct-user attribution. Naming timing must account for that fact without assuming that a completed assistant turn means the user's task has been completed.

The [session manager](https://github.com/earendil-works/pi/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/session-manager.ts) reads the newest name across all entries. ```


## Legacy provenance and scope

The local legacy checkout was inspected at `21b636eaccc487a08362165ec69ffe364e8730fb`: `packages/pi-stuff/src/session-naming/{index,controller,state,prompt,model,settings}.ts`, `conversation-ui/{index,agent-run-origin}.ts` and ADR 0020. These files were unchanged. GitHub could not resolve the commit on the current repository, so this is local-only evidence. The fork came from `pi-autoname`, required English 2-4-word titles and 3-30 ASCII-character validation, used recent six-message context and a ten-minute default cooldown, and defaulted manual-name protection off. Its historical ADR does not govern the rebuilt repository.

The old successful-settlement proposal and default periodic cooldown are therefore not adopted as conclusions of this expanded report. Naming before a reply, after settlement, after early clarification, and after a session has ended are all real patterns in the surveyed systems. Which is suitable here depends on the desired balance between early discoverability and correction of an initially unclear task.

No runtime behavior, configuration, dependency or persistence format was changed. Live model quality, costs and end-to-end host lifecycle remain unmeasured. This report supports the next design discussion; implementation and its concurrency/persistence review require a separately agreed scope.

## Design interview: confirmed decisions and open questions

Automatic generation is restricted to the session opening. Later task changes, resume and compaction do not trigger generation. An explicit user command may generate a replacement later; it does not restart automatic management. This supersedes the earlier discussion of resuming automatic management and following later goal changes. Manual names remain authoritative until the user explicitly changes them or requests a generated replacement.

Generated names use English and the format `type: Action object`, without a parenthesized scope. The maintainer prioritizes minimum token consumption. Goose's first-three-user-message approach was an example, not a selected policy; no three-message threshold is agreed. After the first exchange ends, make at most one automatic naming request using the first user request and bounded final assistant text. Tool output, process logs and thinking are excluded. This does not imply that the first exchange has resolved all ambiguity.

Automatic generation does not retry after failure or invalid output; the default display remains available and the user may invoke the command. Explicit generation names the currently agreed main task, rather than preserving the opening task or listing the conversation's history. Exact input bounds, manual-generation context, model routing and remaining lifecycle boundaries still need agreement. No implementation is authorized by these partial decisions.

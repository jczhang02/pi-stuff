# 在宿主重新加载时缓存未变化的套件模块

## 背景

Pi 0.84.2 每次执行 `/reload` 都会新建一个关闭运行时模块缓存的 Jiti 加载器。这保留了源码编辑语义，但 Pi Stuff 软件包拥有很大的 TypeScript 模块图；即使套件源码没有变化，再次求值仍会主导原本很短的宿主重载时间。交付编译后的 JavaScript 可以降低这项成本，但会形成被禁止的第二条 `dist/` 通道，并使源码与运行时产物分叉。

## 决策

生成的软件包入口继续保持为一个很小的 TypeScript 包装器。它为完整的 `src/` 树计算指纹，并在按源码根目录区分的进程全局缓存中保存一个已导入的套件运行时命名空间。源码未变化时，`/reload` 只复用该模块命名空间。它仍会使用新的 `ExtensionAPI` 运行套件工厂和每一个能力安装器，因此宿主会得到新的处理器、工具、命令、UI 绑定和生命周期所有权。

Pi 在使旧扩展运行器失效前，会发送原因为 `reload` 的 `session_shutdown`。因此，会话作用域的模块状态必须由该事件释放。对于有意跨越无变化重载而存活的进程作用域缓存，其所属能力仍需负责，且不得保留过期的宿主 API 或会话 UI 上下文。

源码缓存遵循以下规则：

- 用 `realpath` 规范化软件包源码根目录，并按该根目录隔离缓存项；
- 以确定性的路径和文件系统元数据，为 `src/` 下每个文件、目录和符号链接计算指纹；
- 对并发加载去重；
- 移除导入失败的结果，使后续重载可以恢复；
- 指纹未变化时复用命名空间并重新运行所有安装器；
- 指纹变化或此前导入失败时，新建一个禁用 `moduleCache` 与 `fsCache` 的 Jiti 加载器，使变化的嵌套模块重新求值，同时不在启动期间写入文件；
- 把宿主提供的 Pi 模块命名空间用作 Jiti 虚拟模块，使刷新路径既适用于源码检出，也适用于已验证的 Bun 二进制文件。

生成的有序组合移至 `src/suite-runtime.ts`；`index.ts` 仍是唯一的 Pi 扩展入口。这两个文件都由 `suite.json` 生成。软件包继续只交付 TypeScript 源码。

## 后果

- 普通的无变化重载会避免重新求值沉重的模块图，同时保留新的扩展注册。
- 编辑任何嵌套套件源码都会使缓存失效，并优先保证正确的源码行为，而非重载延迟。
- 改变源码后的刷新会刻意更慢，因为 Pi Stuff 不写入私有转译缓存。
- 软件包为少用的源码刷新路径新增一个精确版本的 Jiti 运行时依赖。
- 生命周期验收必须证明两条路径：无变化重载复用命名空间，嵌套源码编辑则会在重载后生效。
- 此缓存不会取代 Pi 软件包发现、会话、扩展运行器或宿主的重载命令。

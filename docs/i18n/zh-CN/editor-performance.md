# Editor 与可视化性能实测

[English](../../editor-performance.md).

2026-09-23 为 [Issue #119](https://github.com/jczhang02/pi-stuff/issues/119) 实测, 比较功能前 `1369773` 与产品代码 `0c997f5`. 普通输入的额外开销较小. 很长的展开草稿存在明确退化; 病态正则虽然不阻塞字符显示, 连续编辑期间仍消耗较多进程 CPU. 这些结果不支持笼统的"没有性能问题"结论. 初次测量只补基准工具与证据, 后续修复与复测记录见下文.

## 环境与方法

Linux 6.19.10-jc-xanmod1、Intel Core i9-13900H、约32 GiB内存、维护者编译的 Pi 0.87.1 / Bun 1.4.0、Terminal Control 1.2.1, fullscreen 100×30. 每个进程使用隔离的配置、工作与会话目录和本地确定性模型. 基线来自 Git archive, 共用相同安装依赖. 不计时真实模型服务. 各基准顺序执行, 机器是共享开发环境, 未绑定 CPU 或固定频率; 小差值与单次最大值不能视为统计上已确定的回归.

输入从驱动发送 `x` 前开始计时, 到原生终端报告 `END_TAGx` 为止. 退格恢复草稿不计入该区间. 三轮交替配置顺序, 每轮每种长度/配置保留30次采样. 每种长度首次编辑单独保存, 不进入汇总. 131,072字符压力场景执行两轮, 共60次. P95按保留样本合并后的 nearest-rank 计算.

通过公开 editor setter 加载完整展开草稿, 避免原生大段粘贴折叠. 长度按 UTF-16 码元计, 不是字节数, 另有八字符标记. 文本反复包含 skill、`Review`、普通内容和中文. 10/100条规则中只有 `review` 命中, 其余为简单不命中表达式, 不能代表所有正则或密集重叠负载. 计时是注入输入到 PTY 观测, 不代表物理键盘/桌面合成器延迟, 也不包含首次大段粘贴. 字符显示计时本身不能证明异步关键词着色已完成.

## 输入结果

下表为P95毫秒, 普通场景每格90次, 压力场景每格60次:

| 草稿字符数 | 基线 | 高亮关闭 | 仅 skill | 10条正则 | 100条正则 |
| ---------- | ---: | -------: | -------: | -------: | --------: |
| 256        |  4.0 |      4.6 |      4.1 |      6.5 |       6.6 |
| 4,096      |  6.2 |      4.5 |      6.9 |      7.9 |       7.5 |
| 32,768     |  7.4 |      5.6 |     11.9 |     13.4 |      13.6 |
| 131,072    |  6.8 |      8.9 |     26.7 |     29.3 |      35.4 |

32,768字符时, 开启高亮给字符显示中位数增加约4–5ms. 131,072字符时, 开启后的中位数为18.6–21.4ms, 基线为3.6ms, 开启后的最慢采样46.2ms. 长草稿代价确实存在. 从源码看, 反复全文匹配和生成全文颜色是可能的来源, 但本次没有通过 CPU profiler 逐个函数归因.

131,072字符运行后的基线 RSS 快照为165–168 MiB, 关闭高亮为165–167 MiB, 开启为180–283 MiB. 这些是整个进程的时点值, 包含运行时、worker、JIT与GC状态, 不是分配差值, 也不能证明内存泄漏. 未测试长时间内存增长.

## 关键词着色完成

单独输入新的` Review`, 同时确认该新词的`R`已使用预期加粗RGB, 不只等待文字出现. 负载反复追加和删除同一后缀. 三轮, 每种长度/规则数各60次颜色采样. 每轮另取10次无输入帧读取作为工具开销校准, 共30次. 数字为毫秒:

| 字符数  | 10条规则着色观测P95 | 100条规则着色观测P95 | 无输入帧读取P95, 10/100条规则 |
| ------- | ------------------: | -------------------: | ----------------------------: |
| 256     |                49.8 |                 46.6 |                   26.3 / 17.4 |
| 4,096   |                57.8 |                 51.0 |                   22.6 / 21.4 |
| 32,768  |                59.5 |                 58.1 |                   28.1 / 18.8 |
| 131,072 |                75.2 |                 80.8 |                   19.6 / 19.1 |

颜色观测时间是上界, 包含帧获取开销以及`waitUntil`的10ms轮询. 无输入读取自身的中位数约13–18ms, 因此表内不能当作纯worker耗时, 也不能简单相减P95. 新关键词颜色均被确认, 无超时; 131,072字符的着色观测P95为75–81ms, 单次最大104ms. RGB确认晚于字符观测, 该差值不能全部归因于产品着色. 未测密集重叠正则或任意表达式的颜色完成时间.

## 消息显示

三轮, 每个修订每种负载在新会话中各发送10次, 每格共30次. 从fixture命令按Enter开始, 到独特的正文结束标记显示为止. Skill展开从原生展开键开始, 到最后一条指令标记显示为止. 包含命令分发和终端观测, 不只是解析器执行. 两个修订的源码相同, 但基线显示chart/tree原始代码, 功能版本显示图形.

| 负载                        | 基线中位数 / P95 | 当前中位数 / P95 |
| --------------------------- | ---------------: | ---------------: |
| 普通消息, 16,000字符        |      31.7 / 78.8 |      32.4 / 86.9 |
| 16棵树, 每棵256节点         |    178.1 / 195.8 |      34.5 / 46.2 |
| 16张热力图, 每张32×63数据格 |      17.0 / 27.2 |      14.0 / 19.9 |
| Skill折叠卡片               |        3.9 / 5.6 |        4.5 / 7.2 |
| 展开16,000字符指令          |      14.7 / 21.0 |      15.0 / 20.0 |

本负载下, 普通消息与skill卡片未出现较大的中位数退化. 普通消息尾延迟有波动: 当前P95为86.9ms, 基线78.8ms, 最大值分别103.4与87.5ms, 不能排除小幅尾延迟变化. 本场景树转换比渲染数千行原始代码更快. 热力图每行包含标签及63个数值格, 实际测试32×63, 不是解析器32×64上限. 未对每种图表或长时间累积会话逐一做基准.

## 病态正则

使用`(a+)+$`和80个`a`后接失败后缀, 三个新宿主各执行30组输入/删除. 字符显示中位数/P95/最大值为2.6/3.7/4.3ms. 但整个进程在2.08–2.11秒壁钟窗口中增加了5.26–5.38 CPU秒, 窗口包含停止输入后的一秒, 平均约占用2.5个CPU核心, 并不是零成本.

随后一秒空闲窗口消耗0–10ms进程CPU. 本机Linux的`CLK_TCK=100`, 计量粒度10ms. 这支持输入结束后恢复的结论, 不代表CPU绝对为零, 也不能将全部CPU消耗归给单个正则worker. Worker隔离保护了文本响应, 超时后的反复重建和运行时工作仍有代价.

## 复现与数据

按固定版本安装依赖后, 在本worktree根目录运行. 宿主路径选择本次维护者编译版本, 更换构建就属于不同环境. 脚本在`finally`中关闭自身会话与驱动, 不新增CI门禁或依赖.

```sh
perf_base="$(mktemp -d)"
git archive 1369773 | tar -x -C "$perf_base"
ln -s "$PWD/node_modules" "$perf_base/node_modules"
export PI_PERF_BASELINE="$perf_base"
export PI_TEST_HOST=/opt/bin/pi
bun tools/performance/terminal-input.ts
bun tools/performance/terminal-input.ts --stress
bun tools/performance/terminal-display.ts
bun tools/performance/terminal-pathological.ts
bun tools/performance/terminal-colors.ts
```

脚本将JSON写入源码标明的临时路径, 可用`PI_PERF_OUTPUT`指定文件. 保留数据: [输入](../../assets/editor-performance/input.json)、[压力](../../assets/editor-performance/stress.json)、[消息显示](../../assets/editor-performance/display.json)、[病态正则](../../assets/editor-performance/pathological.json)、[颜色观测](../../assets/editor-performance/colors.json).

## 性能修复与复测

修复以 `7c35b91` 为基线, 其产品代码仍为原 `0c997f5`. 本次缓存不变草稿的 skill 范围, 只为可见范围生成颜色并保留完整匹配的 Unicode 渐变相位, worker 正则只编译一次, 用排序后的线性扫描取代逐个候选遍历所有 skill. 失败 worker 退出后才允许替代实例启动. 冷却期间只保留最新草稿, 从1秒开始, 连续失败翻倍至最多30秒, 成功后重置. 不编辑就不会自动重试失败草稿.

移除原有全文 palette 身份缓存, 改为直接计算可见范围: 默认 skill 匹配原本每次重绘都返回新数组, 导致缓存失效. 不稳定匹配对象和屏外颜色分配的回归测试已先失败后通过. 另补原生 editor 滚动相位、同一 matcher 超时恢复以及冷却期间关闭的回归覆盖.

同一维护者编译宿主和负载顺序运行. 下表用本轮重新测量的修复前默认高亮对比修复后配置, 样本数及交替顺序同前, 数字为 P95 毫秒:

| 字符数  | 修复前, skill | 修复后, 关闭 | 修复后, skill | 修复后, 10条正则 | 修复后, 100条正则 |
| ------- | ------------: | -----------: | ------------: | ---------------: | ----------------: |
| 256     |           4.7 |          5.6 |           5.2 |              4.5 |               5.5 |
| 4,096   |           9.8 |          5.2 |           5.7 |              5.3 |               6.9 |
| 32,768  |          12.8 |          5.6 |           6.2 |              5.3 |               6.6 |
| 131,072 |          27.5 |          5.6 |           7.4 |              7.5 |               9.3 |

131,072字符默认高亮 P95 降低约73%, 中位数20.9 → 5.4ms. 修复后100条规则最大11.4ms. 这证明本负载得到改善, 不表示零开销或任意正则的上界. 新基线列是修复前已开启高亮, 不是前文的功能前基线. 未重新测量修复前10/100条规则输入, 其历史结果保留在上方.

131,072字符的10/100条规则 RGB 观测 P95 为53.0/57.1ms, 历史值75.2/80.8ms. 所有颜色均观测到, 但32,768字符/100条规则有一次182.6ms (P95为62.3ms). 帧读取、轮询与共享机器波动仍存在, 不能称尾延迟已消失. 本轮未改消息渲染代码, 原消息性能证据仍适用, 功能E2E重新运行.

复现修复对照时, 将归档基线由 `1369773` 换成 `7c35b91`, 从修复后 checkout 运行输入脚本. 颜色脚本测当前选定包. 原始数据: [修复后输入](../../assets/editor-performance/fixed-input.json)、[修复后压力](../../assets/editor-performance/fixed-stress.json)、[修复后颜色](../../assets/editor-performance/fixed-colors.json).

病态正则的延长对照包含输入阶段加一秒、随后一秒、再后两秒空闲. 修复前在1.96–2.13秒输入窗口消耗4.92–6.12 CPU秒, 随后一秒0–30ms, 最后两秒10ms. 修复后在1.92–2.01秒输入窗口消耗1.04–1.13 CPU秒, 随后一秒720–760ms, 最后两秒0–10ms. 各窗口总CPU从4.93–6.16降为1.77–1.89秒, 对应各轮约降低62–70%. 输入P95修复前3.4ms, 修复后3.3ms.

冷却将一次排队请求移到了第一个空闲窗口, 不代表每个空闲窗口都零开销. 延长观测确认本轮输入最终停止计算, 不会自动不断重试. 任意复杂正则仍可能消耗CPU, 后续安全编辑也可能等待当前冷却结束. 这些短时测试不覆盖持续病态编辑或长期内存增长. 修复前运行同一病态脚本时设置 `PI_TEST_PACKAGE=<基线归档>`, 测当前包时取消该变量. 原始数据: [修复前病态正则](../../assets/editor-performance/before-fix-pathological.json)、[修复后病态正则](../../assets/editor-performance/fixed-pathological.json).

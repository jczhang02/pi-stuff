## 1. 如何读这份 spec

本文按使用过程排列, 不再按提问轮次排列. 每个界面说明用户要看什么、能做什么、怎样返回. 已确认的方向来自 UIR01-UIR09 和正式 spec; 用户在 dogfood 中明确提出的横线、耗时与消息折叠要求也保留. 修复期间由实现者选择的具体布局参数单列于第 10 节, 不伪装成逐项确认过的设计.

图 1-8 是此前讨论过的 **ImageGen 概念图**, 用于回忆设计意图. 图中的报告、路径、用量和测试结论是示例. 图 9 是 **真实原型截图**, 只说明目前的实现结果. 后续文字决策优先于旧图的快捷键和排版细节.

视觉参考是当时核对过的 Ghostty/Pi 环境: 英文界面、Catppuccin Latte, JetBrainsMono Nerd Font Mono / Symbols Nerd Font Mono / LXGW WenKai Mono, 12pt、关闭连字、2px padding, 默认 150×50. 同时考虑暗色主题及 120×36、80×24. 这是历史参考, 不是本轮重新读取的当前系统配置; 概念图也不保证真实字体栅格和 cell 几何.

## 2. 主界面: FleetView 留在 statusline 下方

### 图 1. 正在主编辑器输入

![图 1. 主编辑器有焦点, FleetView 保留但不显示局部帮助](../../assets/subagents-redevelopment-ui/08-editor-focus.png)

从上到下固定为主对话、主编辑器、主 statusline、FleetView. statusline 指目录、模型和用量区域. FleetView 占满可用宽度, icon 与 statusline 左边缘对齐, 不额外缩进. main 只显示名称, 没有 description.

图中用户正在补充调查要求. 插入光标属于主编辑器; FleetView 行仍可见, 但不显示自己的快捷键帮助. 不为子代理再造一个主会话.

### 图 2. 焦点进入 FleetView

![图 2. 只改变选中 icon, 操作提示在列表上方](../../assets/subagents-redevelopment-ui/09-fleet-focus.png)

选中 lifecycle 时只改变圆圈, 不保留整行高亮、额外箭头或左侧 gutter. 实心圈代表当前键盘选择, 不代表该子代理已成为宿主当前会话. 失焦时隐藏选择强调, 内部记住上次位置.

FleetView 有焦点时, 帮助位于 **statusline 下方、列表上方**; 焦点返回编辑器后隐藏. 图 1 的空白行不是必须预留的永久空间.

| 行组件         | 决策                                                                 |
| -------------- | -------------------------------------------------------------------- |
| 名称           | 不显示 T1/T2 等任务编号. 同名角色需要靠任务描述区分                  |
| 描述           | 简短说明当前任务; 不把完整 prompt 塞进一行                           |
| 耗时           | `34s`, `45m 14s`, `1h 2m`, 不再显示 `2714s`                          |
| tokens         | `↓ 8.2k tokens`, 指本次执行输出, 不是累计输入或全部用量              |
| 正常工作       | 不额外显示 Running                                                   |
| Waiting 等状态 | 与指标共用尾部区域, 右边缘一致; 不能把下方几行挤到另一套列位置       |
| 整体对齐       | 按整组行统一计算名称、描述、耗时和 tokens 的字符宽度, 不逐行拼接空格 |

状态变化不重排行或抢焦点. 超过可见范围时保持选中项可见并提示范围. 已完成、失败和停止的子代理仍能重新打开, 没有子代理时不显示空 FleetView.

## 3. 详情: 替换底部交互区域

### 图 3. 工作中的子代理

![图 3. 主对话保留, 下方直接展示子代理最新内容与工具轨迹](../../assets/subagents-redevelopment-ui/04-detail-working.png)

打开 lifecycle 后, 上方仍是主对话. 下方由子代理详情接管, **主编辑器、主 statusline 和 FleetView 不同时保留**. 整宽横线划分主对话与详情. 这是一块检查区域, 不是 overlay, 也不是伪造的 agent 会话切换.

第一屏应能回答: 这是哪个子代理, 当前在做什么, 最新发现是什么, 是否需要我处理. 信息顺序为:

1. 紧凑身份/任务标题, 本次耗时及输出 tokens.
2. 可展开的 Prompt, 位于主要输出上方.
3. 当前失败或待答问题优先; 否则显示最新可见回复, 完成后直接显示报告.
4. 简短 Activity 工具轨迹, 详细证据按需打开.
5. 与当前状态有关的局部操作提示.

图中的树形缩进用于工具调用及其局部内容, 不把 Prompt、Progress、Result、Errors 等做成同等醒目的分类目录. 最新回复直接使用子代理原文, 不额外调用模型生成 UI 摘要. Prompt 展开后不重复显示同一段任务文字; 完成或输入时 Activity 默认折叠.

| 阅读入口   | 用来回答什么                                            | 返回关系                                     |
| ---------- | ------------------------------------------------------- | -------------------------------------------- |
| 详情主体   | 现在的发现、问题、报告或错误是什么?                     | 返回来源 FleetView 或 graph, 恢复选择        |
| Transcript | 它实际收到什么、说了什么、调用了哪些工具?               | 返回详情; 保留完整已记录内容, 不承诺隐藏推理 |
| Info       | 生效的模型、工具、目录、worktree、Git 结果和用量是什么? | 返回详情; 内容只读                           |
| History    | 同一子代理之前几次交办各有什么结果?                     | Info → 历史列表 → 旧报告; Esc 逐层返回       |

旧报告只读, 不把针对旧执行的操作偷偷发给当前执行. 回到主界面时恢复主编辑器草稿. 关闭详情不停止明确派发的后台工作.

## 4. 关系展示: 独立任务用列表, 依赖任务用 graph

独立的三个调查员就是图 1/2 中的列表. 不为它们画虚构连线或统一套一棵树. 明确存在依赖时才提供 graph 入口, 串行链和 DAG 使用同一种有向图表达.

### 图 4. 两项调查汇入审查员

![图 4. 真实依赖边从两个前置任务指向 reviewer](../../assets/subagents-redevelopment-ui/07-dependency-graph.png)

图中 packages 已完成, lifecycle 仍在执行, reviewer 等待它所需的结果. 下方解释应来自真实调度状态, 不能看到箭头就推断一切等待都由依赖造成.

**这是从 FleetView 打开的关系页面, 不是要求用户在 tree/list/DAG 三种模式之间切换.** 图中的 `j/k select` 是旧提示, 后续已确定优先使用 Pi 配置的选择键, 默认 ↑/↓. 图中框大小、节点间距不是最终 cell 尺寸要求.

选中节点后打开与 FleetView 相同的详情, 返回时恢复 graph 选择. 同名角色附任务描述以便区分. 大图需要有界视口, 选中节点不能消失; 超出视口的连线要有延续标记, 不能为简化排版删边.

## 5. 交互: 留在详情里完成

### 图 5. 回复子代理的问题

![图 5. 原问题与明确收件人的 Reply 编辑器](../../assets/subagents-redevelopment-ui/14-question-reply.png)

`Waiting for main` 表示等待父代理, 不表示必须由人回答. 父代理仍可正常回复; 用户进入详情不会独占该问题. 用户选择 Reply 后, 本地编辑器明确命名收件人, 原问题保持可见且只出现一次.

发送必须绑定打开时的那个问题. 若父代理已答、问题已过期或任务已取消, 保留草稿并说明情况, 不能把旧答案发给新问题或转为 steer. 只有回复被接受后才收起编辑器, 是否恢复工作由实际状态决定.

| 动作            | 实际例子                                                              | UI 应表达的事实                                              |
| --------------- | --------------------------------------------------------------------- | ------------------------------------------------------------ |
| Message / steer | lifecycle 正在调查, 用户补充 "只检查 missing-branch 路径, 不修改文件" | 显示明确收件人; 接受后保留原文与 Queued, 不声称 Read/Applied |
| Reply           | 子代理问 "复现还是只读源码?", 用户回答 "只读源码"                     | 回答当前阻塞问题, 与给工作中 agent 追加指令不同              |
| Resume          | 调查因失败或停止结束, 用户要求接着做                                  | 条件满足时继续同一保存上下文; 不自动重启下游                 |
| Follow-up       | reviewer 已报告, 用户要求复查修复                                     | 新增一次执行记录, 旧报告仍可读                               |

这些动作复用一个局部 composer 模式, 不各做一套 dashboard. 输入时字母 `m/x/p` 都是文字, 不触发详情快捷键. Esc 不发送并保留本次会话中的目标草稿, 发送失败和 resize 也不应丢失它. 不承诺跨进程重启保存未发送草稿.

### 图 6. 停止前在详情里确认

![图 6. 内联停止确认, 不弹出 overlay](../../assets/subagents-redevelopment-ui/15-stop-confirm.png)

停止操作指向当前子代理. 确认前它继续工作, Esc 撤回确认. 确认后显示 Stopping, 直到执行和该请求的收尾真正结束才显示 Stopped. 保留已有输出; 不把 "已请求停止" 误报成 "已停止并保存".

图中 reviewer 会被跳过是因为它依赖 lifecycle, 独立的 packages 不受影响. 这不等于取消整棵递归树. 停止也不代表回滚已经写出的文件. 图中的保留声明表达意图, 保存失败必须另行可见.

### 图 7. 完成后继续交办

![图 7. 旧报告可见, 下方编写 Follow-up](../../assets/subagents-redevelopment-ui/21-follow-up-compose.png)

未发送前, Done 和指标仍属于上一次执行. 接受新请求后展示新执行状态, 旧报告、耗时、用量保留于 History. 续聊仍是同一子代理上下文, 不自动重跑前置或下游. 图中 `68s` 是旧示例, 按后续耗时决定应为 `1m 8s`.

## 6. 可观测性: 状态、模型输出和保存结果不能混淆

### 图 8. 报告完成, 但代码保存失败

![图 8. Done 与 Commit failed 同时呈现](../../assets/subagents-redevelopment-ui/22-commit-failed.png)

图中模型已经交付报告, Git 因磁盘问题未保存提交. UI 保留报告, 同时优先展示实际保存失败. Done 不等于提交成功, 更不等于代码已合并到主目录. 模型报告里的 "tests pass" 是模型文字, 不是 UI 认证的验收结论.

| 实际情况               | 紧凑状态                      | 详情应保留                             |
| ---------------------- | ----------------------------- | -------------------------------------- |
| 等前置结果             | Waiting                       | 哪些真实前置尚未完成                   |
| 波次屏障或并发容量不足 | Queued                        | 已知的调度原因, 不编造依赖             |
| 尚在启动               | Starting                      | 当前阶段及可用配置                     |
| 正常执行               | 耗时与输出用量                | 最新回复及真实工具活动                 |
| 等父代理回答           | Waiting for main              | 原始待答问题                           |
| 指令待消费             | Queued 指令反馈               | 原文; 不替换任务执行状态               |
| 请求取消但未收尾       | Stopping                      | 最新输出, 可返回及阅读, 不提供冲突操作 |
| 执行成功               | Done                          | 原报告, 本次指标                       |
| 失败 / 停止 / 依赖跳过 | Failed / Stopped / Skipped    | 实际原因, 未完成内容, 合法的下一步     |
| 普通执行的 Git 收尾    | Finalizing                    | 不误报 Stopping, 不提前宣称保存成功    |
| 保存提交失败           | Commit failed, 可与 Done 并列 | 完整错误及保留目录, 不显示成功保存     |

缺失用量显示不可用, 不编造 0. 输出为空不等于会话不存在. 单次工具失败不一定意味着整个 agent Failed. 请求在创建 child 前被拒绝时, 主对话显示派发错误, 不凭空创建子代理行或 Transcript.

主对话中的 `subagent` 调用及后台消息属于编排证据, 应像其他工具消息一样可折叠/展开. 默认紧凑, 必要完整内容仍交给父模型. 用户主要阅读父代理最终结论, 想追溯时再展开证据. 不在主对话重复灌入所有旧报告.

## 7. 键盘与焦点合同

必须适合 60 配列和 tmux 使用. 默认方向键仅在 Pi 编辑器、历史和补全都未消费操作的边缘进入 FleetView; `/subagents` 是明确入口. 不用 Alt+A, 不要求功能键、Home/End 或 PageUp/PageDown.

| 当前焦点       | 已记录操作                                                                      |
| -------------- | ------------------------------------------------------------------------------- |
| 主编辑器       | 保留 Pi 编辑、历史、补全; 编辑器边缘 ↑/↓ 进入 FleetView                         |
| FleetView      | Pi 上/下选择键; 确认打开子代理, 确认 main 返回编辑器; `g` 打开已有依赖图        |
| 详情           | `p` Prompt, `a` Activity, `t` Transcript, `i` Info, `g` 已有 graph              |
| 详情干预       | `m` 对应当前可用的 Message/Resume/Follow-up; `x` 停止确认; 确认键回复 live 问题 |
| 阅读           | `[`/`]` 翻页, 显示位置; 有新输出时 `f` 跟随最新                                 |
| Info / History | `h` 从 Info 进入历史; Pi 选择/确认打开旧报告                                    |
| 局部输入       | Pi 原生编辑、提交和换行绑定; Esc 保留草稿并返回                                 |
| 主对话工具消息 | Pi 工具展开绑定, 通常为 Ctrl+O                                                  |
| 返回           | Esc 固定返回上一层, 恢复原焦点和选择                                            |

提示使用实际配置的键, 不写死与 matcher 不同的提示. 详情功能字母只在对应局部界面生效. 原型当时对全局快捷键在检查区域内的传递方式, 不应被误读为新的产品决策.

## 8. 长内容与小屏

保留身份、必要状态、输入及返回入口, 正文有界分页. 内容增长不能让底部区域无限增高. 离开最新页后固定正在读的内容, 新回复只提示有更新, 用户按 `f` 后再跟随; resize 保持阅读位置的语义, 不是只保持一个旧行号.

省略的路径、完整错误、报告和用量必须可以深入查看. Graph 超出屏幕仍保留选中节点与边的含义. 小到无法提供有效界面时显示尺寸提示和 Esc. 使用 Pi 语义主题、字符宽度及换行, 不能只在一种英文长度和一个浅色尺寸下对齐.

## 9. 从 Pi 与 Claude 借什么

| 来源                    | 已确定借鉴                                                  | 不随之引入                                     |
| ----------------------- | ----------------------------------------------------------- | ---------------------------------------------- |
| Claude FleetView        | 焦点相关帮助放在列表上方; 紧凑列; 快速看任务                | active-session 标记、额外指针、宿主 agent 切换 |
| Claude 详情 / peek 思路 | 先看最新有用内容或问题, 再看完整证据                        | overlay、附着到另一个宿主会话                  |
| Pi                      | 原生 editor、Markdown、工具/消息 renderer、按键、主题及通知 | 复制编辑器或访问宿主私有容器                   |
| Codex                   | 按整组分配列宽, 窄屏减少次要字段, 选中项保持可见            | 全行高亮、侧栏、宿主任务切换                   |

Pi 公共组件不等于现成的 subagent 详情页. 已研究的扩展 API 中, `belowEditor` 位于 footer 前, 单靠它不能把 FleetView 放到 statusline 后. 公共 footer/editor 组合是已选择的实现方向; 原生 FooterComponent 所需的完整会话在普通扩展 context 中不可直接取得, 不应靠类型伪造或私有字段补齐. 这些是实现约束, 不是用户需要记住的界面概念.

## 10. 暂停时仍需 review 的具体落点

用户已明确不满意当前产品. 以下内容留作审阅对象, 不在本轮替用户重新定案.

| 已有目标                     | 修复期具体选择                                            | 文档如何处理                                               |
| ---------------------------- | --------------------------------------------------------- | ---------------------------------------------------------- |
| 长报告要有足够空间           | 面板最多约 3/4 屏, 主对话至少留 6 行                      | 保留记录, 不称这个比例已达到满意效果                       |
| Activity 应容易找到          | 显式按 `a` 后移到报告前, 每个工具块先显示有限行           | 是当前落点, 不升级为不可改的视觉要求                       |
| Fleet 显示真实工作与排队反馈 | 描述在任务文字/正在执行工具之间切换, 尾部显示 queued 数量 | 已做过修复, 是否足够稳定易读仍可 review                    |
| 编排消息不能淹没主对话       | 紧凑通知仍可能有逐任务和整批两种消息                      | 折叠与父代理结论的职责已确定; 最终通知密度未获新的满意确认 |
| 简洁而完整的详情             | 多个局部字母入口及当前帮助换行                            | 记录按键合同, 不把当前帮助密度当作最终美观结论             |

# 会话 UI 性能观测

[English](../../../docs/ui-performance.md) · 以英文版为准.

复用 Pi 原生结果组件后, Ctrl+O 重复展开中位耗时从1,174 ms降至33 ms. 后续宽度检查修改在新一轮对照中, 将首次展开从1,097 ms降至102 ms. 这些是保留检索输出的局部实验, 不代表 [#106](https://github.com/jczhang02/pi-stuff/issues/106) 的完整性能验收.

## 负载与测量方式

实验在同一台 Linux x86_64 开发机上使用 Pi 0.87.0 编译宿主、Bun 1.4.0 和 Terminal Control 1.2.1. 每次通过已有 Pi 终端夹具加载真实扩展, 使用新的临时配置与会话、确定性本地 provider、默认暗色主题及100×36终端. 所有条件都关闭欢迎页和两项 RTK 转换. UI 开启时, 检索聚合保持默认设置.

每次先执行40轮用户请求, 每轮连续调用八次 Read, 读取同一份300行 TypeScript 文件. 最后一轮 Write 写入100行 TypeScript: 共321次工具调用, 保留96,000行 Read 源码, 会话文件大小为4,962,321字节. Provider 用单个事件传入每次工具参数, 因此不衡量按时间分批的模型流式输出.

会话生成后测量十次草稿输入、十次交替 Ctrl+O, 以及60、120、80、100、60、120列六次缩放. 展开以最后一行写入源码可见为结束, 收起以该行消失为结束. 耗时包含 Terminal Control 输入分发和屏幕观测; 启动耗时包含夹具准备与宿主启动. CPU、RSS 仅测 Pi 进程, 不包含 provider 和终端驱动. 随后新建五次会话, 每次八个 Read 后再次观测资源, 未强制垃圾回收.

基线为 `b3655a4`, 六次按 UI 关/开/开/关/关/开顺序执行. 最终缓存版本再执行三次 UI 开启的测量. 每个条件有三次独立进程样本、30次输入、三次首次展开、12次重复展开、15次收起及18次缩放. 开发机未专用或固定 CPU, 样本量较小, 不把细微差异判为已确认的退化或提升.

[原始观测数据](../../assets/ui/retrieval-performance.json)保留各次耗时、资源快照、基线 commit 和最终检索源码 SHA-256. 测量使用调用 `launchPi` 的一次性脚本, 没有新增例行 benchmark 套件.

## 初次缓存实验结果

下表均为中位数. CPU 为累计 user 与 system 时间之和, RSS 为对应时刻的驻留内存.

| 观测项                      | UI 关闭 | 缓存前 UI | 缓存后 UI |
| --------------------------- | ------: | --------: | --------: |
| 准备与启动, ms              |     708 |       650 |       771 |
| 生成会话, ms                |   6,721 |     6,107 |     6,716 |
| 草稿输入, ms                |     2.1 |       2.9 |       2.1 |
| 首次全局展开, ms            |   6,094 |     1,208 |     1,248 |
| 重复全局展开, ms            |   6,045 |     1,174 |        33 |
| 全局收起, ms                |      47 |        30 |        33 |
| 收起状态缩放, ms            |    11.5 |       8.0 |       8.5 |
| 生成会话的 CPU 时间, ms     |   6,956 |     6,633 |     7,294 |
| 测量交互期间的 CPU 时间, ms |  32,754 |     6,435 |     1,663 |
| 生成会话后 RSS, MiB         |     335 |       396 |       395 |
| 测量交互后 RSS, MiB         |     663 |       669 |       405 |
| 五次新会话后 RSS, MiB       |     622 |       527 |       351 |

最终缓存的重复展开为30–38 ms, 缓存前为1,089–1,341 ms. 更简单的基线在每次展开状态变化时返回新结果组件. 现在通过 Pi 的 `lastComponent` 保留组件, 仅缓存当前宽度的折行结果, 按需缓存着色后的行; 内容、主题或宽度失效时丢弃布局. 收起的 metadata 不排版. 此结果支持保留缓存, 无需另建历史记录存储.

内存数据不能证明没有泄漏. 会话刚生成时, UI 开启的 RSS 仍比关闭高约60 MiB, 交互结束和新会话后的 RSS 则更低. 分配时机和垃圾回收未受控. 此版本的首次展开仍处理全部保留输出, 有可见停顿.

## 避免首次展开时重复扫描 ANSI

在 `06768a2` 上重新对比, 沿用相同脚本、编译宿主和321次调用负载. 修改前三次首次展开为1,061–1,177 ms, 修改后三次为100–107 ms. 在同一开发机上先测修改前、再测修改后, 顺序执行. [后续观测记录](../../assets/ui/retrieval-width-performance.json)保留各次样本、源码哈希和探针结果.

| 观测项, 中位数            | 修改前 | 修改后 |
| ------------------------- | -----: | -----: |
| 首次全局展开, ms          |  1,097 |    102 |
| 重复全局展开, ms          |     31 |     31 |
| 草稿输入, ms              |    2.4 |    2.2 |
| 收起状态缩放, ms          |    8.2 |    7.5 |
| 测量交互期间 CPU 时间, ms |  1,505 |    401 |

单独的96,000行探针将主要耗时定位到着色行的截断: 约842 ms, 折行约35 ms. 即使行已放得下, Pi 的截断函数仍扫描带 ANSI 的文本. 结果 renderer 现在先用 Pi 的 `visibleWidth` 测未着色正文, 已容纳的行直接返回, 可能溢出的行仍用原截断. 没有增加缓存或排版抽象. 探针对比了测着色行与测正文两种方式, 返回文本哈希均相同; 测正文还能免去 ANSI 和前导栏解析.

此负载重复读取 ASCII 源码, 受益于 Pi 的 ASCII 宽度快速路径. Unicode 正确性另有检查, 尚未测量大量 Unicode 的性能. 分段探针在同一进程内顺序执行, 含预热和缓存顺序影响; 真实宿主对比则每次新建进程. 两种对比都未控制 CPU 调度, 也不构成数值验收预算.

## 验证范围

初次缓存增量的检索、分组和错误测试在 Pi 0.85.1 与 Pi 0.87.0 编译宿主均为19项通过、两项已知 reload/resume 回归失败, 各182次断言. 最终按需处理 metadata 的调整后, 独立验证在两个宿主各通过加强后的同宽换肤测试16次断言, 并通过真实组件的20次断言, 覆盖部分/最终结果、正文替换、warning/error 和 metadata 变化. 换肤测试同时检查窄屏折行, 以及文件改变后重新展开历史结果不读取新文件.

宽度检查修改后, 相同三组测试在两个宿主均为20项通过、两项历史失败; 固定版本193次断言, 编译版本192次, 后者的 reload 在等待阶段失败, 未到下一条断言. 新宿主测试检查60/80/120列的 CJK 与组合字符完整显示, 修改生产代码前也已通过. 另一个 renderer 对照通过2,640组前后布局比较、5,280次断言, 覆盖亮/暗主题、11个选定宽度 (1–7、12、60、80、120列)、四种结果块和收起/展开/部分输出. 这些对照证明行内容不变且不越界, 不代表完整生命周期验收.

尚未约定数值验收预算. 本实验不代表长历史 resume、分批流式输出、滚动延迟、展开状态缩放、欢迎页启动、真实窗口交互或真实模型长时间会话验收. 这些检查、资源归因、待决的历史/assistant 集成方案及最终全量 diff 审查仍需在完整交付前完成.

# 会话 UI 性能观测

[English](../../../docs/ui-performance.md) · 以英文版为准.

复用 Pi 原生结果组件后, Ctrl+O 重复展开中位耗时从1,174 ms降至33 ms. 后续宽度检查修改在新一轮对照中, 将首次展开从1,097 ms降至102 ms. 这些是保留检索输出的局部实验, 不代表 [#106](https://github.com/jczhang02/pi-stuff/issues/106) 的完整性能验收.

## `0221b6f` 当前版本对照

六个新进程按 UI 关/开/开/关/关/开顺序完成测量, 使用 Pi 0.87.0 编译宿主、Bun 1.4.0 和 Terminal Control 1.2.1. 每次40轮、每轮八次 Read, 最后一次 Write, 共321次调用、96,000行保留 Read 输出, 会话文件4,976,301字节. Write 探针100行, 每行含40个 CJK 字符. 两组均关闭 RTK 转换与自动压缩, 欢迎页保持默认. Provider 单事件发出工具参数.

[当前原始数据](../../assets/ui/current-layout-performance.json)保留六次样本、24次布局校准、资源快照和一次性测量脚本. 存档中的源码路径用 `<WORKTREE>` 替代. 早先开启自动压缩的尝试不纳入结果, 因为确定性 provider 无法完成摘要. 旧的收起态 `resizeMs` 也排除, 因为它可能在 Pi 完成正文重排前满足等待条件. 下文历史收起态缩放数据具有同样限制, 不能证明重排性能.

| 观测项, 中位数         | UI 关闭 | UI 开启 |

| 重复全局展开, ms       |   5,918 |      36 |

| 校准后展开态缩放, ms   |   4,727 |     107 |

| Resume 至末尾标记, ms  |      49 |      73 |

每组有三个进程样本、30次输入、三次首次展开、12次重复展开、15次收起、12次展开态缩放、12次滚动观测和九次 resume/reload 循环. Resume 范围为关闭时38–80 ms、开启时68–89 ms; reload 分别为107–145 ms和115–155 ms. Resume 中位额外耗时约24 ms. 这组样本未出现开启 UI 后恢复停顿数秒的情况, 但不能据此保证所有会话的性能上限.

展开态缩放先在60/80/100/120列校准: 最后一行源码必须保留完整40个 CJK 字符和末尾标记, 且显示行宽距目标宽度不超过四格. 24次校准记录的宿主与画面列数全部一致. 随后的计时等待正文与校准行完全匹配. 滚动等待 PageUp 出现更早的源码行范围, PageDown 返回原底部范围. 测量的是目标内容出现, 不保证整帧稳定, 也不代表未见宽度的首次布局耗时. 交互 CPU 包含校准和资源观测命令.

全部18次 resume/reload 循环均未改变原会话文件字节. 启动包含夹具准备与宿主启动, 不证明欢迎页完整绘制. Reload 以操作就绪和末尾标记为结束, 不保证最终画面已经重新绘制. RSS 是瞬时值而非峰值, 垃圾回收与宿主调度未受控; 小样本不能证明没有泄漏. 分批流式性能与真实模型长时间测试仍未完成.

下文实验描述旧版本. 历史 Read/检索/Web 恢复失败已通过显示 lookup 集成处理, 当前证据见 [UI 集成](ui-integration.md). 五列组合字符前导栏溢出已在 `0221b6f` 修复, 两个宿主各通过14项测试、108次断言. 这些结果不代表所有 Unicode 都正确或完整验收完成.

## 负载与测量方式

实验在同一台 Linux x86_64 开发机上使用 Pi 0.87.0 编译宿主、Bun 1.4.0 和 Terminal Control 1.2.1. 每次通过已有 Pi 终端夹具加载真实扩展, 使用新的临时配置与会话、确定性本地 provider、默认暗色主题及100×36终端. 所有条件都关闭欢迎页和两项 RTK 转换. UI 开启时, 检索聚合保持默认设置.

每次先执行40轮用户请求, 每轮连续调用八次 Read, 读取同一份300行 TypeScript 文件. 最后一轮 Write 写入100行 TypeScript: 共321次工具调用, 保留96,000行 Read 源码, 会话文件大小为4,962,321字节. Provider 用单个事件传入每次工具参数, 因此不衡量按时间分批的模型流式输出.

会话生成后测量十次草稿输入、十次交替 Ctrl+O, 以及60、120、80、100、60、120列六次缩放. 展开以最后一行写入源码可见为结束, 收起以该行消失为结束. 耗时包含 Terminal Control 输入分发和屏幕观测; 启动耗时包含夹具准备与宿主启动. CPU、RSS 仅测 Pi 进程, 不包含 provider 和终端驱动. 随后新建五次会话, 每次八个 Read 后再次观测资源, 未强制垃圾回收.

基线为 `b3655a4`, 六次按 UI 关/开/开/关/关/开顺序执行. 最终缓存版本再执行三次 UI 开启的测量. 每个条件有三次独立进程样本、30次输入、三次首次展开、12次重复展开、15次收起及18次缩放. 开发机未专用或固定 CPU, 样本量较小, 不把细微差异判为已确认的退化或提升.

[原始观测数据](../../assets/ui/retrieval-performance.json)保留各次耗时、资源快照、基线 commit 和最终检索源码 SHA-256. 测量使用调用 `launchPi` 的一次性脚本, 没有新增例行 benchmark 套件.

## 初次缓存实验结果

下表均为中位数. CPU 为累计 user 与 system 时间之和, RSS 为对应时刻的驻留内存.

| 观测项                      | UI 关闭 | 缓存前 UI | 缓存后 UI |
| --------------------------- | ------: | --------: | --------: |
| 准备与启动, ms              |     708 |       650 |       771 |
| 生成会话, ms                |   6,721 |     6,107 |     6,716 |
| 草稿输入, ms                |     2.1 |       2.9 |       2.1 |
| 首次全局展开, ms            |   6,094 |     1,208 |     1,248 |
| 重复全局展开, ms            |   6,045 |     1,174 |        33 |
| 全局收起, ms                |      47 |        30 |        33 |
| 收起状态缩放, ms            |    11.5 |       8.0 |       8.5 |
| 生成会话的 CPU 时间, ms     |   6,956 |     6,633 |     7,294 |
| 测量交互期间的 CPU 时间, ms |  32,754 |     6,435 |     1,663 |
| 生成会话后 RSS, MiB         |     335 |       396 |       395 |
| 测量交互后 RSS, MiB         |     663 |       669 |       405 |
| 五次新会话后 RSS, MiB       |     622 |       527 |       351 |

最终缓存的重复展开为30–38 ms, 缓存前为1,089–1,341 ms. 更简单的基线在每次展开状态变化时返回新结果组件. 现在通过 Pi 的 `lastComponent` 保留组件, 仅缓存当前宽度的折行结果, 按需缓存着色后的行; 内容、主题或宽度失效时丢弃布局. 收起的 metadata 不排版. 此结果支持保留缓存, 无需另建历史记录存储.

内存数据不能证明没有泄漏. 会话刚生成时, UI 开启的 RSS 仍比关闭高约60 MiB, 交互结束和新会话后的 RSS 则更低. 分配时机和垃圾回收未受控. 此版本的首次展开仍处理全部保留输出, 有可见停顿.

## 避免首次展开时重复扫描 ANSI

在 `06768a2` 上重新对比, 沿用相同脚本、编译宿主和321次调用负载. 修改前三次首次展开为1,061–1,177 ms, 修改后三次为100–107 ms. 在同一开发机上先测修改前、再测修改后, 顺序执行. [后续观测记录](../../assets/ui/retrieval-width-performance.json)保留各次样本、源码哈希和探针结果.

| 观测项, 中位数            | 修改前 | 修改后 |
| ------------------------- | -----: | -----: |
| 首次全局展开, ms          |  1,097 |    102 |
| 重复全局展开, ms          |     31 |     31 |
| 草稿输入, ms              |    2.4 |    2.2 |
| 收起状态缩放, ms          |    8.2 |    7.5 |
| 测量交互期间 CPU 时间, ms |  1,505 |    401 |

单独的96,000行探针将主要耗时定位到着色行的截断: 约842 ms, 折行约35 ms. 即使行已放得下, Pi 的截断函数仍扫描带 ANSI 的文本. 结果 renderer 现在先用 Pi 的 `visibleWidth` 测未着色正文, 已容纳的行直接返回, 可能溢出的行仍用原截断. 没有增加缓存或排版抽象. 探针对比了测着色行与测正文两种方式, 返回文本哈希均相同; 测正文还能免去 ANSI 和前导栏解析.

此负载重复读取 ASCII 源码, 受益于 Pi 的 ASCII 宽度快速路径. Unicode 正确性另有检查, 尚未测量大量 Unicode 的性能. 分段探针在同一进程内顺序执行, 含预热和缓存顺序影响; 真实宿主对比则每次新建进程. 两种对比都未控制 CPU 调度, 也不构成数值验收预算.

## Bash 展开与更简单的方案

在 `56e32f1` 上, 另一组以 Bash 为主的会话重复展开中位耗时为563 ms. 每个新进程先执行15轮, 每轮八次 `cat source.ts`, 每次返回同一份400行 ASCII 文件, 随后 Write 写入100行. 共121次调用、48,000行 Bash 输出, 会话大小为2,458,436字节. 编译宿主、隔离 provider、配置、终端尺寸和交互测量沿用上述方式, 但本实验没有执行五次新会话循环.

基线按 UI 关/开/开/关/关/开运行. 随后对复用 `lastComponent`、折行和着色结果的缓存候选测量三次. 独立审查要求再比较更简单的方案: 仅在着色截断前检查 `visibleWidth`, 仍创建新结果组件. 此版本也测量三次, 最终采用. [Bash 观测记录](../../assets/ui/bash-performance.json)保留全部十二次数据及候选/源码哈希.

| 观测项, 中位数            | UI 关闭 | 修改前 | 缓存候选 | 仅宽度检查 |
| ------------------------- | ------: | -----: | -------: | ---------: |
| 首次全局展开, ms          |   2,177 |    545 |       34 |         60 |
| 重复全局展开, ms          |   2,222 |    563 |       29 |         53 |
| 全局收起, ms              |     171 |     50 |       28 |         50 |
| 草稿输入, ms              |     4.0 |    1.5 |      1.6 |        1.7 |
| 收起状态缩放, ms          |     9.0 |    9.4 |      7.7 |        7.6 |
| 测量交互期间 CPU 时间, ms |  12,619 |  3,330 |      462 |        656 |
| 生成会话后 RSS, MiB       |     327 |    281 |      304 |        280 |
| 测量交互后 RSS, MiB       |     590 |    485 |      335 |        323 |

选用的修改将重复展开降至49–61 ms. 在此负载中, 额外缓存还能减少约24 ms中位耗时, 但需要分别维护正文/着色状态及失效路径. 宽度检查已消除大部分可见停顿, 改动也更小, 因此舍弃缓存候选. 这不是新增验收阈值. RSS 受分配与垃圾回收时机影响, 这些样本不能证明泄漏或保证内存节省.

新增真实宿主测试检查运行态尾部预览、追加输出、完成后改为前三行、同宽换肤、反复展开和60/80/120列 CJK 折行. 此测试在优化前的基线上已通过. 最初版本截到了 resize 中间帧; 改为等待指定宽度和完整行后通过, 未为此修改产品. 最终工具、流式、终端输出和 RTK 结果测试在固定 Pi 0.85.1 与编译 Pi 0.87.0 上均通过28项、197次断言. 这些功能检查不衡量分批流式更新的性能, 也未解决已知历史恢复失败.

独立审查通过3,600次与基线逐行一致的比较, 覆盖两种主题、12个宽度 (0–7、12、60、80、120)、十种文本及多种预览/结果状态. 额外宽度断言发现既有边界: 五列时, 前置组合/spacing 字符序列 `\u0301\u093eX` 可产生测量为六列的行. 审查者确认22个此类溢出案例在修改前后完全一致. 此证据证明本次优化的等价性, 不证明所有 Unicode 宽度都正确; 该边界后续在 `0221b6f` 修复, 见上文.

## 验证范围

初次缓存增量的检索、分组和错误测试在 Pi 0.85.1 与 Pi 0.87.0 编译宿主均为19项通过、两项已知 reload/resume 回归失败, 各182次断言. 最终按需处理 metadata 的调整后, 独立验证在两个宿主各通过加强后的同宽换肤测试16次断言, 并通过真实组件的20次断言, 覆盖部分/最终结果、正文替换、warning/error 和 metadata 变化. 换肤测试同时检查窄屏折行, 以及文件改变后重新展开历史结果不读取新文件.

宽度检查修改后, 相同三组测试在两个宿主均为20项通过、两项历史失败; 固定版本193次断言, 编译版本192次, 后者的 reload 在等待阶段失败, 未到下一条断言. 新宿主测试检查60/80/120列的 CJK 与组合字符完整显示, 修改生产代码前也已通过. 另一个 renderer 对照通过2,640组前后布局比较、5,280次断言, 覆盖亮/暗主题、11个选定宽度 (1–7、12、60、80、120列)、四种结果块和收起/展开/部分输出. 这些对照证明行内容不变且不越界, 不代表完整生命周期验收.

尚未约定数值验收预算. 本实验不代表长历史 resume、分批流式输出、滚动延迟、展开状态缩放、欢迎页启动、真实窗口交互或真实模型长时间会话验收. 上文当前对照补充了限定范围的 resume、滚动和展开态缩放证据. 分批流式、完整欢迎页绘制、真实模型长时间会话及最终全量 diff 审查仍需验收证据; 历史/assistant 集成方案已不再待决.

# Subagent rewrite design

[简体中文](i18n/zh-CN/subagents-design.md) · English is normative.

Status: source-reviewed design proposal in [#64](https://github.com/jczhang02/pi-stuff/issues/64). The maintainer accepted the interview answers through Q60, then requested a full source review before UI. This working draft incorporates the [decision review](subagents-decision-review.md), which identifies retained rules and proposed revisions against the accepted baseline at `1c75955`. The revisions are recommendations, not new maintainer approvals. F01-F33 remain required; no product behavior has been implemented or accepted.

## Accepted decisions

- Use @arhen/pi-core-subagent as the source for a fork and rewrite. Design the UI independently, without adopting upstream's UI design.
- Work in this order: establish core behavior, explore UI scenarios and prototypes, then settle implementation interfaces and structure. UI exploration may expose core behavior that needs revisiting.
- Decide capabilities individually. Tool names, parameters and configuration may be redesigned; upstream compatibility is not a requirement imposed on this design.
- Every supported capability needs acceptance in a real usage scenario. Parallel, serial and other supported execution modes each need their own acceptance coverage; one primary scenario cannot stand in for the full feature set.

The maintainer requested a plain feature inventory before capability selection. Q14 established the distinction between a subagent and a subagent task; Q32-Q33 clarified skipped tasks and task baselines; Q47 distinguished cancellation in progress from a task that has stopped; Q60 distinguished reported completion from acceptance by the main agent. These terms are recorded in [the glossary](../CONTEXT.md). The rules below are the consolidated review proposal. Their original answers and changes are traceable through the decision review; inventory alone does not settle runtime semantics.

## Accepted tool entry point

After reviewing [pico §8.5](https://github.com/earendil-works/pi/blob/ceea48f5d5d12fd7915dfefba2835ccd55f23bb9/packages/agent/docs/pico/pico-v3.md#85-subagents), the maintainer selected one model-facing tool named `subagent`, with a `command` field selecting the operation. This fixes the entry-point shape; the command set and parameters remain for interface design. Ordinary messages, steering, follow-up assignments, waiting and cancellation retain their distinct behavior and applicable authority. A single tool does not require a single implementation module or adopting pico's background-cancellation policy.

## Capability selection

Q3-Q9 confirmed all upstream capabilities F01-F29 as required. This includes execution modes and result delivery, task control, communication, role and resource configuration, limits and accounting, worktree management, persistence and lifecycle events. Every capability needs real-scenario acceptance coverage.

Retaining a capability does not accept upstream parameter names, default values or known defects. The current rules below incorporate the review revisions; unresolved implementation mechanisms remain open.

## Task and context rules

- **Q14, identity and task history:** Retain the subagent's logical identity and recoverable conversation history across assignments; a live SDK runtime may be unloaded and recreated, and ephemeral tool caches are not implicitly durable. Keep a separate record, reported outcome and immutable result references for each task. Each delegated task records which parent task created it. A later assignment to a retained agent does not reopen an earlier parent's completed task. Follow-up does not replace earlier results or automatically rerun their consumers.
- **Q15, recursive limits:** The root task tree shares execution concurrency, cumulative admitted-task counts and a maximum delegation depth. These count different things: waiting can release an execution slot, but does not erase task history, reset depth or refund cumulative allowance. Retaining a context in memory is not active execution. Q24 defines dispatch boundaries; Q26 gives provisional values.
- **Q16, completion:** A task cannot complete while descendants delegated by that task are still executing or awaiting execution. This lifetime follows task ownership, not every future assignment to a retained descendant agent. A backend lead waits for the database work it delegated; its old task does not become pending when the main agent later assigns that database agent new work. Q23 and Q55 govern failure handling and final delivery.
- **Q17, cancellation:** Cancelling a task cancels its entire descendant branch and prevents new descendants from starting. Retain existing records and code artifacts for inspection. Cancelling the backend lead also stops its database and API children.
- **Q18, tool and permission ceiling:** A descendant's tool scope and effective execution permissions cannot exceed its parent's applicable ceiling. Roles and calls only narrow them. Tool names are an exposure filter, not a filesystem, network or process sandbox. A read-only researcher asks an authorized ancestor to arrange write work; copying history does not grant tool authority.
- **Q19, history snapshot:** Copy the parent's visible history at a valid session-fork boundary, preserving completed messages, tool results and existing compaction summaries. Handle pending tool calls so the child receives valid call/result pairs; any generated fork-control record must be identified as such, not presented as an executed tool result. Later parent messages require explicit communication. History copying does not copy live tool handles, permission grants or workspace state.

## Scheduling, failure and recovery rules

- **Q20, busy-agent follow-up:** A new assignment to a busy subagent enters its queue. The subagent executes one task at a time. A reviewer finishes its login review before starting a queued payment review; a correction to its current review uses steering instead.
- **Q21, waiting and concurrency:** An explicit descendant or answer wait releases an execution slot only when that task has no model request or other tool still executing. Resuming must reacquire a slot through the queue. Waiting keeps identity, mailbox, ownership and cumulative counts. Leads waiting for children must not prevent those children from running; a parallel test tool still running prevents early slot release.
- **Q22, dependency failure:** A dependency that settles without an eligible completed result prevents its consumers from starting, while unrelated branches continue. This includes execution failure, cancellation, a declared inability or a missing fulfillment declaration. Its unstarted consumers become skipped under Q32 unless already cancelled directly. Report the reason rather than leave them waiting forever.
- **Q23, descendant failure:** Report a child's failure to its direct parent, allowing the parent to delegate again or complete the work itself. Keep the child's failure record. One child failure does not immediately cancel the whole tree or automatically make the parent fail; the parent can recover and still complete its assignment.
- **Q24, limits across dispatches:** All dispatches in one main session share execution concurrency. Each top-level dispatch and its descendants have a cumulative task allowance. Follow-ups to its retained agents remain charged to that dispatch; wrapping follow-up in another tool call does not reset the allowance. A separately created top-level dispatch has its own allowance, but cannot bypass main-session concurrency. The main session owns top-level background dispatches, so ending its response does not join them. A child's background flag changes waiting, not parent-task ownership or descendant join/cancellation rules.
- **Q25, restart recovery:** Restore subagent contexts and task records when reopening the parent session. Completed subagents can receive follow-up tasks. Unfinished tasks are marked interrupted and require explicit continuation by the main agent or user. Already executed write operations are not automatically replayed.

## Limits, dependency scheduling and code handoff

- **Q26, provisional configurable defaults:** Use eight concurrent execution slots per main session, sixty-four cumulative accepted tasks per top-level dispatch, and delegation depth three with the main agent at zero as configurable trial values. Initial assignments, recursive assignments and follow-ups count; Pi provider-request retries do not create another task. These values are not benchmarked recommendations. Scenario acceptance must exercise smaller configured limits and record resource use before treating defaults as calibrated.
- **Q27, execution clock:** Count time spent in model and tool execution stages toward the task's execution limit. Exclude queueing and explicit waits for descendants or answers. Answer waiting has a separate timeout. A researcher waiting half an hour for an answer does not consume half an hour of execution time.
- **Q28, ready-task scheduling:** A task can start as soon as its own dependencies are satisfied and an execution slot is available. It does not wait for unrelated tasks in the same batch. API implementation can start after its thirty-second investigation while a five-minute database investigation continues.
- **Q29, dependency recovery:** Keep the original graph and its failure records after repairing a failed task. The main agent explicitly dispatches subsequent work referring to the new result. Do not automatically restart the skipped tasks in the old graph when a replacement investigation succeeds.
- **Q30, write isolation:** Give each writable subagent in a Git repository its own worktree by default. Serialize its assignments in that workspace; independent agents do not share a writable working copy. Worktree setup failure is startup failure, never permission to fall back to the original directory. Q34 defines follow-up and baseline changes.
- **Q31, combining code:** Use a saved commit or other fixed artifact reference for code dependencies, not a moving branch tip. One upstream artifact can be inherited directly. Multiple write artifacts require an explicit integration task to merge them and resolve conflicts; later tasks consume its saved artifact. A follow-up advancing an upstream branch must not change an already accepted downstream input.

## Task outcomes, workspaces and message scope

- **Q32, skipped tasks:** A task ends as skipped when it cannot start because a settled dependency did not produce an eligible completed result. Retain that dependency and reason. Direct cancellation remains cancellation, not a skip alias. If A reports inability before B starts, B has a terminal outcome and its parent does not wait indefinitely.
- **Q33, initial baseline:** Include tracked uncommitted changes in an isolated initial baseline; include untracked files only when explicitly selected. Leave the original working tree and index unchanged. If the source changes while the baseline is being captured, detect that and retry or report capture failure instead of silently combining revisions. A child can therefore use a freshly edited interface without requiring a parent commit.
- **Q34, follow-up workspace:** A write follow-up normally reuses the subagent's retained worktree and records its actual starting baseline. Preserve each earlier result's commit and diff references even when the branch advances. A different baseline is an explicit caller choice; prepare that workspace and rebind session resources before execution. Do not silently reset partial work or reuse tools bound to an old directory.
- **Q35, code delivery:** Save the task's intended code changes on its own branch and return fixed commit/diff references with check evidence. Saving code and declaring the assignment fulfilled are separate outcomes. If saving fails, retain and report unsaved work. The main agent explicitly decides whether to apply the artifact; the worker must not stage unrelated files or treat a branch name as immutable delivery.
- **Q36, cleanup:** Keep a retained subagent workspace available for follow-up. Once its workspace is explicitly released, automatically reclaim it only after execution has stopped and all non-reproducible content is saved or explicitly disposed of. Inspect tracked, untracked and ignored content; a clean commit alone is insufficient. Retain result references and session records until explicit cleanup. Uncertain or unsaved content prevents removal and is reported.
- **Q37, non-Git writes:** Allow the caller to explicitly choose direct writes in a specified non-Git directory, such as a plain document folder. Unisolated writes are not the default.
- **Q38, message scope:** Agents within the same top-level dispatch can address one another by known ID, including across delegation levels. Upward questions go to the direct parent by default. The main agent relays communication between separate dispatches. A database agent can send its field conventions directly to the API agent in the same dispatch.

## Message delivery, configuration and extension state

- **Q39, ordinary messages:** Store messages with their target agent and task association, then deliver them before the next model processing step without interrupting running tools. Receipt is not evidence that the model has consumed the message. Messages for an ended task are retained and reported to the main agent without automatically starting a new assignment or altering the old result.
- **Q40, unanswered questions:** Default answer waiting to ten minutes, configurable. On expiry, explicitly report that no answer arrived. The child may continue independent work or report that it cannot complete the assignment; do not invent an answer or automatically fail the whole task. A late reply remains associated with the original question and does not automatically start another task.
- **Q41, role selection:** Let the dispatcher explicitly select a discovered Markdown role or define one inline. Use a generic role when none is specified. Retain role files and their discovery list, but do not automatically select or switch roles by text similarity. Mentioning a database in a review assignment does not select a database implementation role.
- **Q42, configuration precedence:** For a new subagent, resolve ordinary values in call, role, project, user, then parent order. Save the resulting configuration. Follow-up uses that agent's saved configuration unless the caller explicitly overrides supported values; role-file edits alone do not change it. Effective tool and permission ceilings always apply, including later restrictions. Q51 specifies per-task records.
- **Q43, dependency result delivery:** Deliver upstream final reports and artifact references, including files, branches and commits, without the entire execution log by default. Above a configurable length, provide a clearly marked truncated preview and a reference for reading the full output. Preserve the full result. A downstream implementer can read a researcher's long report in full when needed.
- **Q44, record recovery:** Persist task creation, important transitions and results, with associations to session and fixed code artifacts. Make durable terminal records available before announcing durable completion. Restore usable records and report missing or damaged parts. Persistence failure is a core failure to report, not an optional event-listener error; no exactly-once replay or automatic replay of writes is promised.
- **Q45, extension state:** Load explicitly selected extension entrypoints with child-owned initialization, context and lifecycle state, then expose only permitted tools. Loading an entrypoint may initialize other tools or hooks in that extension; a tool allowlist cannot prevent those side effects. Do not reuse parent handler closures or mutable extension runtime. Support requires verified session-safe behavior; unavailable or unsafe entries fail explicitly. Independent factories do not prove isolation of arbitrary module globals, external services or subprocesses.

## Execution control and recovery boundaries

- **Q46, execution timeout:** Keep a configurable cumulative execution deadline using Q27. Leave that deadline disabled unless explicitly configured; remove the unvalidated universal thirty-minute cutoff. A configured expiry requests cancellation of the task and its descendants, retains artifacts and records timeout as the cause, with Q47 governing actual stopping. It never automatically reruns the assignment. Individual tool/provider limits remain independent.
- **Q47, cancellation in progress:** A cancellation request is not confirmation that execution has stopped. Keep the task cancelling while a tool is still running; active execution continues to occupy its slot. Do not start the same subagent's next task or clean up its workspace before stopping is confirmed. Report activity that has not stopped, such as a test process remaining after cancellation.
- **Q48, bounded result waits:** Use sixty seconds as a configurable trial value for one main-agent result wait. Relevant completion, questions or failures wake it early. Expiry returns current information and ends only that wait, not child execution. Use event-driven wakeups; this value is not a polling interval or an instruction to wake the model repeatedly when nothing changed.
- **Q49, steering:** Prioritize instructions that change the current task after the current turn's tools finish and before the next model call. Do not forcibly stop those tools; the work remains the same task. If the task has already ended, explicitly reject steering and direct the caller to follow-up. An instruction to prioritize login fixes over payment work takes effect at that boundary.
- **Q50, invalid dispatches and admission:** Validate known graph, role/tool, depth and cumulative-limit errors and reject the entire invalid dispatch without creating tasks or consuming allowance. Reserve admission consistently before any accepted task starts; concurrency shortages queue valid work. Failures after admission, such as worktree creation, are recorded startup failures of accepted tasks and do not roll back already running unrelated work. Whole-dispatch validation is not a transaction over arbitrary runtime side effects.
- **Q51, configuration snapshots:** Record the complete effective configuration of each accepted task. A new agent uses Q42's resolution; a follow-up starts from the agent's saved configuration plus explicit supported overrides and applicable ceilings. Editing a reviewer role from model A to B must not silently change that retained reviewer. A newly created agent can use the new role definition. Changing a queued or running task requires an explicit supported operation, not hot reload.
- **Q52, read-only code view:** In Git repositories, default read-only tasks to an independent snapshot of the specified code baseline. Reading the live workspace requires explicit selection. A reviewer must not silently combine code from before and after the main agent's concurrent edits.
- **Q53, missing workspace recovery:** If a workspace is missing and its saved code commit is available, rebuild that saved code state and rebind the restored session to it; execution still requires explicit continuation. A commit cannot restore unsaved or ignored content that was never preserved, so report those gaps. Missing required context or code blocks restoration; never fall back silently to the parent directory or a different baseline.
- **Q54, event listener failures:** Optional lifecycle observers must not change task outcomes or stall scheduling when they fail; record their extension errors. Required state persistence and artifact saving are not optional observers and their failures remain visible core errors under Q35 and Q44. A broken progress logger must not invalidate completed work, but a missing result record cannot be called saved.

## Final delivery, session lifetime and authority

- **Q55, final parent report:** A parent task joins the descendants it delegated. If it reports before their outcomes have been consumed, wait without an execution slot and resume that same task to incorporate the new outcomes before final delivery. If it already explicitly waited and incorporated them, do not force an extra model turn merely to summarize again. A normal model-turn ending alone cannot bypass this task-level join.
- **Q56, queued tasks after abnormal outcomes:** Keep the conservative rule that abnormal outcomes hold the same agent's remaining uncancelled queue, without affecting other agents. Treat this as an explicit queue policy, not an inferred dependency between every assignment. Let the authorized caller select a recovery assignment before releasing the held queue, or continue/cancel queued work. Receiving an ordinary message never releases it automatically. Recovery can release only independent, uncancelled queue entries; tasks owned by a cancelled branch remain cancelled.
- **Q57, main-session lifetime:** A real Pi session switch or normal exit stops its child tasks and saves unfinished work as interrupted for explicit restoration. Merely finishing a response or changing UI focus does not end that session. A crash cannot confirm that external work stopped; report and reconcile unknown activity before resuming in the affected workspace. No detached cross-session execution is implied.
- **Q58, management authority:** The main agent manages the whole task tree. A subagent may manage only its own descendant branch. Peers can communicate within the agreed message scope, but cancelling, steering or assigning follow-up to a peer requires an ancestor with management authority. A database agent may alert the API agent to a problem but cannot unilaterally cancel its task.
- **Q59, default read-only tools:** A default read-only role exposes reading, search and extension tools confirmed to provide read-only capabilities. It does not expose arbitrary shell execution or write-capable extensions. When command execution is needed, such as running tests, an authorized ancestor explicitly arranges the appropriate tool configuration and isolated workspace.
- **Q60, assignment outcome:** Record execution termination, the subagent's declared assignment outcome, and main-agent acceptance separately. A normal turn ending or successful process exit does not prove fulfillment. Dependents require a settled task with an explicit fulfilled declaration and required results/artifacts saved and readable; an absent declaration, inability or runtime failure does not release them. This declaration is not proof of correctness: test/review evidence and main-agent acceptance remain separate. The later interface design must carry this outcome explicitly, without requiring arbitrary business-output schemas.

The [decision review](subagents-decision-review.md) covers every Q1-Q60 decision and distinguishes source facts from our choices. The [acceptance scenarios](subagents-acceptance.md) now follow this consolidated proposal. No product scenario has been executed. Overall review of these revisions precedes UI; interfaces, source structure and isolation mechanisms remain later work.

## Upstream boundaries and rewrite decisions

- F10 has a known initialization-time cancellation gap: a later state update can overwrite cancellation and allow execution to continue. A dedicated pause operation is absent; cancellation followed by F11 is only a partial substitute.
- F11 accepts failed/aborted tasks, not completed-task follow-ups. An explicit replacement model can also be overridden again by a matching role file.
- F21 disables extensions in the child loader. Loading project rules/skills does not establish extension-tool inheritance.
- F26 can fall back to editing the original directory when worktree creation fails; Q30 replaces this with startup failure. Dependencies in node_modules are shared through a symlink rather than isolated. Commits are saved for parent review; automatic merge is not an upstream runtime feature.
- F27 selects one completed upstream branch, not a merge of all upstream branches. Q31 requires an explicit integration task when several branches must be combined.
- F28 writes the sidecar at whole-run settlement. It is not continuous crash-safe checkpointing, and restoring records does not automatically replay the workflow.

The upstream gaps in completed-session follow-ups, parent-history copying, child-created subagents and extension-tool loading are addressed by accepted additions F30-F33 and the rules above. Their implementation and scenario acceptance remain pending.

Other capabilities absent from upstream include runtime graph mutation, saved workflow templates, conditional loops, automatic acceptance gates, human approval nodes, model-output schemas, hard usage budgets, cross-run role memory, external-agent backends and periodic scheduling. These have not been accepted into the rewrite scope.

02 / Native Pi 0.83 proposals

三个流程的差别，是你何时离开 BTW

三案关闭时都占零行，主 transcript 都不会出现 BTW 问答。A 看完一答就回主线；B 可以停留追问；C 发出后立即回主线、以后自己来取答案。

A

单次快问：回答完停在这里，看完关闭

BTW 只承担“根据主会话已经知道的内容，回答这一个问题”。需要继续讨论或调用工具时，提升为已有 Agent/session，而不是让 BTW 长成第二个聊天。

为什么选定

边界最清楚，也最接近 Claude。BTW 不会逐渐取代 main conversation 或 Agent。

真实代价

主任务继续计算，但你正在阅读 BTW 时不能同时输入主提示；需要澄清只能再问一次或提升为 session。

B

临时侧线程：留在这里继续追问

这是当前 @narumitw/pi-btw 最接近的使用形态。BTW 有自己的 composer；你可以继续对话，也可以把选中答案放回 main draft，但关闭便丢弃整条临时线程。

什么时候更舒服

第一答通常需要澄清时，不必反复关闭和重新打开 BTW；现成 Package 也已验证这条能力路径。

为什么不先推荐

BTW 变成第二条聊天后，用户容易在里面停留很久；它与 main session、Agent session 的职责边界开始模糊。

C

静默信箱：问完立刻回主线，以后再来看

这是唯一真正让用户也能立刻继续主对话的方案。但我们已经拒绝 BTW widget、statusline 和 transcript 通知，因此正常屏没有任何地方告诉你答案是否完成。

实际优点

用户和主 Agent 都能继续，BTW 完全不会抢占长期屏幕空间。

为什么不推荐默认

除非新增另一种通知渠道，否则用户必须反复打开 BTW 才知道结果；失败也可能静默。

03 / Genuine Claude Code 2.1.220 evidence

Claude 的关键不是画法，而是关掉以后主任务真的还在那里

隔离 fixture 故意让 main request 延迟，同时回答 BTW。release binary 的真实行为显示：BTW 暂时占据焦点；Esc 后 main live row 恢复，而且 fixture 的 main response 此时仍未返回。证据证明 BTW 没有取消主任务，但没有捕获更晚的主任务完成状态。

04 / Selected direction · 2026-08-01

已确认 A：把 BTW 保持为真正的“顺便问一句”

A

一次回答足够；更大的问题交给已有 session 系统

B 更宽容，但它把 BTW 变成另一条聊天。C 让用户马上回主线，却没有自然的完成反馈。A 的限制反而让 BTW、main conversation 和 Agent 三者边界最容易理解。

  1. 一条 side question 只产生一条 no-tool answer；main Agent 同时继续计算。
  2. BTW 只在非浮动 Command Dialog 中出现；关闭时正常屏零占位。
  3. routine Q/A 不进入 main transcript/context；session-local history 可以重开与清除。
  4. 关闭 BTW 永不取消 main Agent，并恢复 dialog 打开时保存的 draft、Todo 与 Agent roster。
  5. 需要继续讨论或新调查时，提升到已有 Agent/session，而不是给 BTW 加工具。
已冻结大结构与 fork base，本轮不冻结：提升动作、复制、历史上限与是否跨 resume、model/provider、最终快捷键、颜色、行数和窄屏阈值。能力将通过 @juicesharp/rpiv-btw@2.3.1 的 Pi Stuff owned fork 进入 Suite，不直接依赖 upstream。

01 / Selected lifecycle

对话记录、当前状态和完整管理，各自只有一个位置

同一事实不应同时塞进 transcript、Todo、roster 和 statusline。三个位置分别回答“发生了什么”“谁还在工作”“我现在要控制什么”。

普通结果不抢焦点

完成、失败和停止留在原有分组记录与 roster 状态中；完整结果进入 Agent Command Dialog。失败必须保留最短原因与 partial-result 提示。

防呆线才接管

界面明确写出哪个 Agent、具体命令和触发原因。只能允许这一个精确操作一次，或用 Esc 拒绝；不提供 session 或持久授权。

用户问题先提醒

子 Agent 的内部提问先交给 main Agent 自动回答。只有 main 判断必须由人回答，才出现持续 attention row；它不吞掉你正在输入的文字。

02 / Genuine Claude Code 2.1.220

Claude 只提供界面与生命周期参考，不替 Pi Stuff 决定授权范围

真实发布版把正在运行的 Agent、主会话说明与权限选择放在同一个终端流中。没有居中的弹窗；权限区域临时取得输入控制。实际 Esc 实验确认：工具调用被拒绝，但后台 Agent 继续并最终完成。它显示的项目级持久允许是 Claude 自己的选择，Pi Stuff 的防呆线不继承该选项。

03 / One coordinator, one surface

防呆线不是再开一层界面，而是切换同一个 Command Dialog 的当前状态

这正是统一协调器存在的原因。BTW、Agents、Tool Details 和 Settings 不能各自维护互不知情的 dialog。高优先级事件在同一个状态机里暂停低优先级内容，因此恢复不依赖私有 Pi API。

04 / Non-modal attention and terminal outcomes

需要回答不等于立刻夺走你正在打的字

这里的 needs input 已经过 main Agent 判断，确实只能由用户决定。它持续显示在 Todo 之前，并把对应 roster 行标为 waiting；但 editor 仍拥有按键。内部 contact_supervisor → reply 不自动升级为这条用户提醒。

05 / Engineering verdict

这套焦点与恢复生命周期在 Pi 0.83 扩展层成立；破坏性识别仍需另行证明

OK

原型只冻结审批形状，不把静态分析包装成安全边界

原型证明的是 UI ownership：一个 Pi Stuff coordinator 可以通过公共 setEditorComponent、widgets、footer 和非 overlay custom() 组合完成焦点与恢复。它没有证明任意第三方 dialog 可被抢占，没有执行画面中的命令，也没有证明所有等价破坏写法都能被识别。

  1. Pi Stuff-owned Command Dialog 共享一个状态栈；破坏性 tripwire 高于 user-input attention，attention 高于 BTW。
  2. 第三方扩展自行打开的 dialog 无法可靠暂停；它占用界面时，高优先级请求只能排队到 Suite 重新获得控制。
  3. 生产 coordinator 必须组合已有 custom editor factory；本隔离原型可以直接安装自己的 CustomEditor。
  4. 生产事件需要稳定 ID、reload 去重和多请求队列；本原型只模拟一个 attention 和一个静态 tripwire。
已选择的 Pi 交互：默认不审批日常工作，命中防呆线时只允许精确一次或拒绝。本原型只验证一个不会执行的固定案例：rm -- /tmp/pi-stuff-tripwire-prototype/obsolete.txt，其目标静态明确且位于 session cwd 外。界面没有“本 session 允许”或持久授权。无法解析的破坏性目标应直接退回 Agent 改写，而不是让用户批准含糊范围。具体首版命令范围、旁路与平台行为仍需独立的对抗测试；该机制不是 sandbox。

# UI direction research and terminal previews

[简体中文](../i18n/zh-CN/research/ui-direction-2026-09-20.md)

This research covers the whole Pi Stuff UI. The old interface is the reference, not a rejected design. Single-line tool output and weak diff presentation are examples of friction within that interface. The maintainer asked for a surface inventory, multi-source research and a coherent preview set before more detailed decisions.

**Status:** proposal for discussion, not an accepted production specification. Research date: 2026-09-20. Task: [#99](https://github.com/jczhang02/pi-stuff/issues/99), Beads `pi-stuff-cgl.1`. Base: `cd0f174`. Pi host: `0.85.1`; Bun: `1.4.0`.

## What exists and what needs attention

Current Pi Stuff registers Web and RTK in `index.ts`; `/rtk` is its current custom panel. The themes are real. Conversation UI, tool presentation and shared diagnostics are not implemented on this baseline. Native Pi still provides the transcript, input editor, model/session selectors and its own tool display. Session identity/naming, Goal, Todo, subagents, background work, BTW and notifications are explicitly outside this pass.

### Public seam boundary

Pi 0.85.1 exposes `setStatus`, keyed `setWidget`, `setHeader`, `setFooter`, `setEditorComponent`, `registerMessageRenderer`, `registerEntryRenderer` and per-tool `renderCall`/`renderResult` in its [extension API](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/src/core/extensions/types.ts). A custom message fixture only proves the renderer for that custom type. It does not replace ordinary assistant text, thinking, or a native `read`/`bash` card.

Native built-in cards do have a public route: register the same tool name, delegate to Pi's `create*Tool` implementation, preserve its exact result/details shape, and override only the render slots needed. Pi documents per-slot renderer inheritance in [the built-in override guide](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/docs/extensions.md), so this is a documented implementation path for native tool cards. Ordinary assistant and thinking components have no equivalent public renderer hook. `registerMarkdownTransformer` can see `assistant-thinking`, but only transforms Markdown before Pi renders it; theme colors and the hidden label remain the supported control points.

`setStatus` is additive. `setFooter` and `setHeader` replace Pi-owned surfaces, and `setEditorComponent` replaces the editor, so each needs one explicit owner and a restore path. This isolated preview makes Pi Stuff the sole header/footer owner. Production coexistence with other packages remains a decision; additive status is the safer integration when another footer owner exists. The old custom UI remains the reference, and these package rows do not create requirements.

The sample preview uses fixture messages and static states only. It has not executed a live provider, tool call, test command or repository mutation, so its screenshots do not establish native runtime behavior.

## Proposed whole-screen direction

The preview preserves the scrolling conversation and Pi's input dock. Welcome, message typography, tools and footer use the same active theme. Tool blocks share a visible hierarchy: action and target, outcome, then content. Their height depends on useful content rather than every tool being forced to one line.

The critical comparison is the whole work session: can the reader see what the session just explained, what it is doing and whether intervention is needed, while keeping the editor available? Making a diff more attractive is insufficient if status counters crowd those elements out.

The fixture follows one task: remove duplicate results across search pages while preserving order and cursor behavior. Scene files represent selected stages, not a recorded real coding run. Test counts, model, cost, timings and loaded inventory are illustrative. No provider, test command or repository mutation is executed by the extension.

See the [runnable prototype](../../prototypes/ui-direction/README.md) and its capture gallery for the complete visual evidence. Adoption remains open: tool density, footer fields, `/tools` list/detail behavior and large-diff navigation should be discussed against these screens. No production entrypoint loads this prototype.

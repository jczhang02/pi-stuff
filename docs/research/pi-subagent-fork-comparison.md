# High-download Pi subagent packages: fork comparison

[简体中文](../i18n/zh-CN/research/pi-subagent-fork-comparison.md)

## Scope and selection

The core comparison is limited to **five high-download packages in the official Pi package catalog**. A candidate must be listed in the catalog, have at least **10,000 npm downloads in the fixed 30-day window**, and provide a reusable child-agent runtime through a Pi package. Candidates are ordered by downloads. Replacement CLI distributions, role/prompt packages without a general dispatch surface, and fixed-purpose commands are outside this comparison. This threshold is a research selection rule, not a Pi certification or a quality score.

The target is daily development with Pi Stuff: fresh-context scouting and independent read-only review, background delegation, status/wait/steer/stop/results, and an explicit existing task-worktree cwd. Pi loads the stable installation while development stays in the task worktree. The target host is Linux Pi 0.85.1 compiled with Bun; the repository uses Bun 1.4.0 and Effect 4.0.0-rc.112. No old Pi Stuff implementation is part of this research.

The catalog snapshot was read on **2026-09-10**. Its default order is “Most downloads”; the first 150 cards were screened through a lower endpoint of 7,568 monthly downloads, below the inclusion threshold. Package names and descriptions were used for discovery, followed by source checks for relevant runtime behavior. The table contains the five highest-download eligible implementations identified in that bounded screening. [Pi package catalog](https://pi.dev/packages).

| Existing cwd        | Supported; worktree features are additional             | Uses host cwd for the child                               | Supported; optional fresh worktree starts from HEAD             | Supported; optional worktree may fall back to shared cwd    | Absolute realpath and directory validation                          |

The facts in this matrix are expanded and linked below. OS process separation, a detached flag, a durable result file, and independent host recovery are different properties. A prompt saying “read only” does not prevent writes. A worktree separates files but does not restrict shell or network permissions.

### pi-subagents: strongest adoption and target-host evidence

nicobailon's package has the highest download count in the shortlist. Its background parent writes runner configuration/status, starts a detached runner and performs a startup handshake before returning. The runner writes status, events, transcripts and results; watchers and persistent artifacts allow later delivery and reconciliation. It distinguishes result completion from observed process exit. [Async startup](https://github.com/nicobailon/pi-subagents/blob/aa75b3353836f7868898e3bd58234d21eaff1463/src/runs/background/async-execution.ts#L398-L448), [runner lifecycle](https://github.com/nicobailon/pi-subagents/blob/aa75b3353836f7868898e3bd58234d21eaff1463/src/runs/background/async-execution.ts#L540-L748).

It already supports fresh/fork contexts, steering, control messages and bounded spawning. Its exact-source upstream run passed unit/integration, Bun parity, Pi 0.85.0/0.85.1 smoke and Linux standalone checks using deterministic providers. This is the closest observed runtime evidence to the intended host, although it is neither a live-provider acceptance run nor a test on the maintainer's installation. [Observed CI run](https://github.com/nicobailon/pi-subagents/actions/runs/34438313918).

The integration cost is 90,437 implementation code lines and 283 files, including missions, scheduler, workflows, external jobs, intercom, worktrees and TUI. The 6,953-line foreground executor also shows concentration inside that broad surface. A fork should first preserve one upstream lifecycle and its tests, then justify each scope reduction. Restrictive reviewer/scout tools and explicit base/head/diff inputs still need host acceptance.

### pi-background-tasks: strong inspect-only delegation, incomplete control API

The package provides ordinary background shell tasks, direct child-Pi delegation and Fusion workflows. Children use the current host cwd and stream outputs to task artifacts. The live registry remains in memory: persisted files do not imply automatic reattachment after restart, and extension shutdown/reload kills live children. `bg_status` and `bg_logs` are snapshots; terminal notifications drive follow-up, while `bg_result` retrieves delegate/Fusion answers. There is no general live steering API. [cwd and child spawn](https://github.com/ismailsaleekh/pi-background-tasks/blob/14aa4ef382952f073bd4d540f57d6e8e3c2789a2/src/core/registry.ts#L780-L905), [shutdown contract](https://github.com/ismailsaleekh/pi-background-tasks/blob/14aa4ef382952f073bd4d540f57d6e8e3c2789a2/src/extension.ts#L54-L60), [inspection and kill tools](https://github.com/ismailsaleekh/pi-background-tasks/blob/14aa4ef382952f073bd4d540f57d6e8e3c2789a2/src/extension.ts#L832-L942).

Its inspect delegate is a useful enforced boundary: allowed tools are `read`, `grep`, `find`, `ls` and `delegate_read_artifact`; shell, edit/write and recursive delegation are denied. Isolated mode disables ambient extensions, skills, templates and context files. An explicit ambient-extension mode weakens that boundary. Each child has its own session identity and a frozen, hashed context seed, so independent identity does not mean zero inherited content. [delegate policy and argv](https://github.com/ismailsaleekh/pi-background-tasks/blob/14aa4ef382952f073bd4d540f57d6e8e3c2789a2/src/core/delegate/launch.ts#L201-L364).

The child commits `result.json` through temporary write, fsync and rename; the parent records a separate outcome. Exit zero without a committed result is failure. These are stronger success semantics than trusting process exit alone. [result commit](https://github.com/ismailsaleekh/pi-background-tasks/blob/14aa4ef382952f073bd4d540f57d6e8e3c2789a2/src/core/delegate/artifacts.ts#L235-L277), [terminal adjudication](https://github.com/ismailsaleekh/pi-background-tasks/blob/14aa4ef382952f073bd4d540f57d6e8e3c2789a2/src/delegate-child-extension.ts#L524-L590).

Its declared Pi peer range ends at the 0.84 series and excludes 0.85.1. The exact-source CI run is **failed**: all six main OS/Node jobs stopped at `Type-safety standard`, skipping their subsequent test and pack steps; two separate Windows integration jobs passed. Detailed diagnostic logs were inaccessible, so the specific rule failure remains unknown. [Observed failed CI](https://github.com/ismailsaleekh/pi-background-tasks/actions/runs/33832119776). Together with missing steering and live-task recovery, these gaps keep it behind the leading fork candidates despite substantial downloads.

### @tintinweb/pi-subagents: smaller in-process alternative

Each child is an independent Pi `AgentSession` within the parent process. `AgentManager.spawn()` returns an ID, separates foreground/background pools, queues excess background work and settles records after cleanup. Sessions, transcripts and tombstones support later continuation, but parent process failure ends active child sessions. [manager lifecycle](https://github.com/tintinweb/pi-subagents/blob/e955e29c51b7a6cce37e1108cd2d6c57a77e151c/src/agent-manager.ts#L430-L705).

It supports steering; stopping is exposed through UI/RPC rather than a direct model stop tool. Optional worktrees start from HEAD, so they omit the parent's uncommitted changes. A reviewer needs the existing checkout or an explicitly supplied patch. [worktree source](https://github.com/tintinweb/pi-subagents/blob/e955e29c51b7a6cce37e1108cd2d6c57a77e151c/src/worktree.ts#L1-L117).

At 12,217 code lines, it is the smallest implementation in this shortlist, while retaining 47,744 downloads in the fixed month. It still includes workflows, mentions, schedules and FleetView. Its source develops against Pi 0.84.2 and declares peers >=0.84.0, which includes 0.85.1. The observed build/floor/latest compatibility jobs succeeded, but the latest compatibility lane is configured `continue-on-error`. [Observed CI run](https://github.com/tintinweb/pi-subagents/actions/runs/33753714643).

### @quintinshaw/pi-dynamic-workflows: recoverable orchestration

The `workflow` tool accepts a script or named workflow and defaults to background execution. A manager persists the run and lease before returning its ID; child agents run as SDK sessions in the same process. The control tool supports list/status/pause/resume/stop. It has no API for a new instruction to an already-running child; named-thread continuation is a script operation. [background tool](https://github.com/QuintinShaw/pi-dynamic-workflows/blob/1c0f7462aa8a007afb8112f073887590a57ea82d/src/workflow-tool.ts#L187-L304), [manager startup](https://github.com/QuintinShaw/pi-dynamic-workflows/blob/1c0f7462aa8a007afb8112f073887590a57ea82d/src/workflow-manager.ts#L563-L692).

After a crash, stale running records become paused. Resume creates a new execution, replays the unchanged journal prefix and runs the remaining calls. It does not reconnect to lost live sessions. Defaults permit 1,000 logical agents and 16 concurrent agents per run; token budget and hard agent timeout are unlimited unless configured. The runtime drains in-flight calls and can wait indefinitely if a runner ignores abort without a finite timeout. [stale-run reconciliation](https://github.com/QuintinShaw/pi-dynamic-workflows/blob/1c0f7462aa8a007afb8112f073887590a57ea82d/src/workflow-manager.ts#L495-L526), [default limits](https://github.com/QuintinShaw/pi-dynamic-workflows/blob/1c0f7462aa8a007afb8112f073887590a57ea82d/src/config.ts#L1-L18), [abort/drain limitation](https://github.com/QuintinShaw/pi-dynamic-workflows/blob/1c0f7462aa8a007afb8112f073887590a57ea82d/src/workflow.ts#L1435-L1500).

Fresh loaders disable ambient extensions while retaining skills/context files; tool plans deny recursive `workflow` and `workflow_control` calls. Optional worktree creation can fall back to shared cwd on failure. That fallback needs an explicit policy if callers rely on isolation. [resource loader](https://github.com/QuintinShaw/pi-dynamic-workflows/blob/1c0f7462aa8a007afb8112f073887590a57ea82d/src/agent.ts#L669-L703), [worktree fallback](https://github.com/QuintinShaw/pi-dynamic-workflows/blob/1c0f7462aa8a007afb8112f073887590a57ea82d/src/worktree.ts#L1-L75).

It is a plausible fork when scripted fan-out and replay are the product. Its 15,430 code lines are substantially smaller than nicobailon's, but it is a workflow runtime rather than a ready replacement for live steer/wait/stop child controls. Its exact-source [CI](https://github.com/QuintinShaw/pi-dynamic-workflows/actions/runs/33803985812) and [release run](https://github.com/QuintinShaw/pi-dynamic-workflows/actions/runs/33804042174) succeeded on Node-based gates; the target compiled Pi host remains untested.

### pi-fabric: broad runtime with explicit process and ownership boundaries

Fabric launches workers through a transport adapter. `auto` prefers herdr, localterm, tmux and screen before falling back to a detached process. Worker state and lifecycle events use files. The agent service authorizes direct-child operations, enforces admission/depth limits, and separates cancelling a waiter from stopping its child. [transport selection](https://github.com/monotykamary/pi-fabric/blob/469926c111bb7cfa419036e6ed86da753671ef53/src/agents/manager.ts#L1485-L1498), [service API](https://github.com/monotykamary/pi-fabric/blob/469926c111bb7cfa419036e6ed86da753671ef53/src/agents/service.ts#L29-L116), [authority and admission](https://github.com/monotykamary/pi-fabric/blob/469926c111bb7cfa419036e6ed86da753671ef53/src/agents/service.ts#L326-L395).

An optional resident host gives durable work an independent owner and file-based request/reply queues. Restart marks in-flight requests as indeterminate rather than assuming success. Service `resume` instead restores a paused/completed/failed child from a checkpoint; these recovery mechanisms must not be conflated. The durable API also rejects full session seeds and several handoff fields. [durable request boundary](https://github.com/monotykamary/pi-fabric/blob/469926c111bb7cfa419036e6ed86da753671ef53/src/residency/host.ts#L577-L703), [checkpoint restore](https://github.com/monotykamary/pi-fabric/blob/469926c111bb7cfa419036e6ed86da753671ef53/src/agents/service.ts#L415-L444).

Its launcher explicitly handles a Bun-compiled Pi binary whose `process.execPath` cannot interpret worker scripts: it resolves a real Node/Bun interpreter or configured binary. This is relevant source evidence, with actual host discovery and extension loading still requiring acceptance. Tool allowlists and QuickJS guest-code isolation address different boundaries; allowing shell in an agent does not become read-only because its orchestration script is isolated. [script runtime resolution](https://github.com/monotykamary/pi-fabric/blob/469926c111bb7cfa419036e6ed86da753671ef53/src/agents/transports/process-utils.ts#L58-L153), [tool allowlist](https://github.com/monotykamary/pi-fabric/blob/469926c111bb7cfa419036e6ed86da753671ef53/src/core/child-tool-allowlist.ts#L1-L13).

The cost is 86,790 code lines, 351 files and 15 direct runtime dependencies, covering actors, mesh, guest-code engines, MCP, memory and tool ownership. Those capabilities are beyond the first delegation feature. The exact-source [Test run](https://github.com/monotykamary/pi-fabric/actions/runs/34396888943) succeeded; that does not establish acceptance of every transport or resident-host failure mode on the target machine.

## Fork recommendation and acceptance

**Use nicobailon's pi-subagents as the primary fork baseline to validate under the high-download requirement. Keep tintinweb as the smaller alternative if an in-process child lifetime is sufficient.** nicobailon combines the strongest adoption signal in this shortlist with the closest observed Pi 0.85.1 standalone evidence and the most complete detached recovery path. tintinweb offers a much smaller codebase with substantial package downloads, at the cost of a different process-lifetime contract and missing direct model stop tool.

The other three have narrower reasons to study them: background-tasks for its inspect-only delegate and committed-result contract; dynamic-workflows for bounded scripted orchestration and journal replay; fabric for participant ownership and interpreter/resident-host boundaries. Their useful mechanisms do not justify combining three runtimes into the first Pi Stuff feature.

Before adopting a fork, validate one complete development flow in the existing worktree: spawn a fresh scout or reviewer, let the parent continue, observe status, collect a bounded result, steer where supported, and stop the child. Include explicit base/head/diff inputs for review, tool registration that actually excludes writes and recursive delegation, cancellation during completion, and parent reload/exit. Choose whether recovery must preserve live work or only resume from saved results/checkpoints, then test that exact contract on Linux Pi 0.85.1 compiled with Bun. Package downloads, source inspection and upstream CI are distinct evidence; none replaces this host acceptance.

## Evidence status

The report uses official catalog/registry/download endpoints, pinned source files, and observed upstream CI runs. Source sizing and document checks were performed locally. Candidate dependencies, extensions, tests, workers and live-provider calls were not installed or executed. Download snapshots may change, publication/source identity is qualified above, and no production fork has been adopted.

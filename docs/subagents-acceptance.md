# Subagent acceptance scenarios

[简体中文](i18n/zh-CN/subagents-acceptance.md) · English is normative.

Status: proposed acceptance coverage for maintainer confirmation in [#64](https://github.com/jczhang02/pi-stuff/issues/64). The [design record](subagents-design.md) contains the accepted F01-F33 scope and Q3-Q60 rules. These tables describe future operations and pass conditions; no scenario below has been executed or passed.

## How to use this specification

Run scenarios through the supported actual Pi host with isolated project, settings and session data, following [quality assurance](quality-assurance.md). A disposable development project should contain a reproducible login bug, a failing test, an independent payment task and branches that can be integrated. Use harmless fixture instructions and data for context and tool checks.

Record the tested revision, host/environment, effective configuration, operations, task identities, observed outcomes and relevant artifacts. Controlled providers can make scheduling, errors and interruption repeatable; identify that environment rather than treating it as evidence of live-provider behavior. Use configured short waits for timeout cases and separately check the documented defaults. UI presentation and exact tool names are not fixed here.

Every F row needs evidence. Boundary scenarios B01-B12 supplement those rows; one combined development workflow cannot replace separate parallel, serial or dependency-graph coverage. Missing environments or evidence remain unverified. The tables are requirements for later verification, not instructions to execute product code during this design discussion.

## Execution and task control

| Capability                      | Actual use                                                                                                                                | Pass condition                                                                                                                                                                                                                                     |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F01 Single delegation           | Ask one researcher to locate the login failure without copying parent history.                                                            | It has its own context and task record; intermediate work stays in its session, and its final result is available to the parent.                                                                                                                   |
| F02 Parallel execution          | Dispatch login and payment investigations together with two available slots.                                                              | Both make progress during overlapping execution periods, retain separate results and stay within the concurrency limit.                                                                                                                            |
| F03 Serial execution            | Dispatch investigation, repair and review as a chain.                                                                                     | Each task starts only after its predecessor completes; the next task receives the required report and code artifact.                                                                                                                               |
| F04 Dependency graph            | Let API implementation depend on a short API investigation, while integration depends on both API and a longer database branch.           | API work starts when its own dependency and a slot are ready; integration waits for both inputs. Invalid graphs and failed dependencies follow B01 and B03.                                                                                        |
| F05 Upstream results            | Give an implementer a long research report and its file/commit references.                                                                | It receives the final report and references, not the whole process log by default. Above the configured length, a marked preview points to readable complete output.                                                                               |
| F06 Background and foreground   | Dispatch once in the background and once with a result wait; let the main agent finish a response while the background task runs.         | Background dispatch returns a usable identity before completion. The wait observes the task, and ending the main response does not stop background work.                                                                                           |
| F07 Status and results          | Query a dispatch and its tasks while queued, executing, waiting, cancelling and ended, then read an earlier result after follow-up.       | Queries identify the current situation and task, expose the associated result/artifact references, and preserve earlier results.                                                                                                                   |
| F08 Bounded waits               | Wait for a slow researcher with a short configured wait, then wait again.                                                                 | The first wait expires with current state while the child continues. Completion, questions and failures wake the relevant wait. Default main-agent wait is sixty seconds.                                                                          |
| F09 Notifications               | Let one researcher complete and another fail while the main agent does other work.                                                        | The parent receives correctly associated completion/failure notifications and can retrieve the matching records; failure is reported without waiting for unrelated work to finish. Dispatch settlement is reported after all its tasks have ended. |
| F10 Cancellation                | Cancel a backend lead with active database and API descendants.                                                                           | The entire branch stops accepting new descendants; execution stops before cancellation settles or workspaces are reclaimed. Existing records and code remain inspectable. See B04.                                                                 |
| F11 Failed/aborted continuation | Fail a repair after it has changed a file, then explicitly continue with the same subagent; repeat with cancellation in a separate trial. | Its available context and partial artifact are used, with a new assignment record and the old outcome retained. No unrelated old graph nodes automatically restart. See B03 and B09.                                                               |
| F12 Steering                    | During a tool call, tell an implementer to prioritize login and defer payment; separately steer all running children in a dispatch.       | Steering is processed after the current turn's tools and before the next model call, within the same task. Steering an ended task is explicitly rejected.                                                                                          |

## Communication and configuration

| Capability                   | Actual use                                                                                                                                   | Pass condition                                                                                                                                                                                                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F13 Ask the parent           | A database child asks its direct parent to clarify a field; run answered, unanswered and late-reply variants.                                | Waiting releases the execution slot. A timely reply resumes work through the queue; expiry reports no answer without inventing one or automatically failing the whole task. Default answer wait is ten minutes. A late reply stays associated with the question. |
| F14 Report a finding         | A researcher reports the likely faulty file, then continues investigating.                                                                   | The parent can read the finding while the child continues without waiting for a reply.                                                                                                                                                                           |
| F15 Agent mailbox            | A database agent sends a field convention to an API agent at another depth in the same dispatch.                                             | Known-ID delivery respects the dispatch boundary; the recipient receives it before its next model processing step. Ended-task and message-scope variants are in B06; management authority is checked in B10.                                                     |
| F16 Inline roles             | Define a temporary release-note investigator with task-specific instructions and limited tools.                                              | The child uses that definition without requiring a role file and stays within the inherited tool ceiling.                                                                                                                                                        |
| F17 Role files               | Discover project and user role files, select a reviewer explicitly, then dispatch without specifying a role.                                 | The selected role is used; the unspecified case uses a generic role. Mentioning a database does not silently select or switch roles.                                                                                                                             |
| F18 Model and thinking       | Set differing model/thinking values in the call, role, project, user and parent configuration, then remove higher-priority settings in turn. | Effective values follow Q42's precedence. A queued task keeps its accepted configuration after role-file edits; a later follow-up resolves new configuration.                                                                                                    |
| F19 Tool selection           | Assign a read-only researcher, a writable implementer and a child requesting tools its parent lacks.                                         | Each receives only allowed tools. The default researcher has no arbitrary shell or write-capable extensions, and descendants cannot widen the parent scope. See B10.                                                                                             |
| F20 Working directory        | Dispatch into the API subdirectory, then explicitly choose a non-Git document folder for a write task.                                       | Relative work uses the intended location within the selected baseline. Non-Git direct writing requires explicit selection; it is not a fallback from failed isolation.                                                                                           |
| F21 Project rules and skills | Place a harmless project instruction and a relevant configured skill in the selected project, then delegate matching work.                   | The child's resource loading uses the intended working directory, and its context/work demonstrates access to those instructions and skill. Loading a skill alone does not grant an extension tool.                                                              |

## Limits, code and records

| Capability                  | Actual use                                                                                                                                      | Pass condition                                                                                                                                                                                                                                                                        |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F22 Resource limits         | Dispatch enough researchers across two top-level dispatches to fill the main session, then create descendants and follow-ups near their limits. | Defaults are eight concurrent tasks per main session, sixty-four cumulative tasks per top-level dispatch and depth three with the main agent at zero. Initial tasks, recursive assignments and follow-ups count; Pi request retries do not. Configured limits also work. See B01-B02. |
| F23 Execution timeout       | Let an implementation task use a short configured execution allowance, including a tool call and explicit waiting phases.                       | Only Q27's execution stages consume the allowance. Timeout stops the task and descendants, retains artifacts and records the cause without automatic rerun. Default execution allowance is thirty minutes. See B05.                                                                   |
| F24 Provider retry          | Cause a retryable provider/network response, then separately cause a failed code test.                                                          | Provider requests follow Pi's configured retry behavior within the same task. A failed test or arbitrary failed assignment does not automatically rerun as a new task.                                                                                                                |
| F25 Usage accounting        | Run a lead, two descendants and a later follow-up, including a provider retry.                                                                  | Per-task input/output/cache tokens, cost and turns are inspectable where available; aggregate totals do not double-count descendants or overwrite earlier tasks. Missing provider measurements are identified rather than invented. No hard token/cost budget is claimed.             |
| F26 Worktree management     | Dispatch two writers from a dirty Git workspace, collect their code and allow eligible worktrees to be reclaimed.                               | They keep separate baselines/artifacts; commits, diffs and checks are returned for the main agent to apply. The original workspace stays unchanged. Setup failure, untracked files and cleanup variants are in B07-B08.                                                               |
| F27 Branch inheritance      | Run a repair followed by review; separately combine two write branches through an integration task.                                             | The single-input task sees the earlier branch. Multiple code branches are explicitly integrated, including conflicts, and later work inherits the integrated artifact.                                                                                                                |
| F28 Persistence and restore | Close or interrupt the main session during a batch, reopen it and inspect completed and unfinished tasks.                                       | Records and contexts are restored where available. Unfinished work is interrupted and requires explicit continuation; saved writes are not automatically replayed. Missing/corrupt records and artifacts follow B09.                                                                  |
| F29 Lifecycle events        | Observe task lifecycle events from an extension, then make its listener throw.                                                                  | Events identify the corresponding lifecycle activity. Listener failures are recorded as extension errors without changing task results or disrupting scheduling.                                                                                                                      |

## Added capabilities

| Capability                       | Actual use                                                                                                                                                           | Pass condition                                                                                                                                                                                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F30 Completed-subagent follow-up | Ask the same reviewer to re-review a revised artifact, both before and after reopening the main session.                                                             | Identity/context are retained, each assignment has its own record/result, and a write follow-up gets a new task branch from the selected previous artifact. Earlier reports remain available and consumed results do not automatically rerun downstream work.    |
| F31 Parent-history copy          | Dispatch one child with a fresh context and another with copied history containing tool results and a compaction summary; send the parent new information afterward. | The copied child receives the complete visible snapshot at dispatch, including existing summaries and tool results. The fresh child does not receive that history. Neither automatically receives later parent messages.                                         |
| F32 Recursive delegation         | A backend lead creates database and API children; one returns late, one fails, and one attempts to delegate beyond its limits.                                       | Shared quotas, depth and tool ceilings hold. Waiting releases slots; the lead handles failures and consolidates descendant outcomes before final delivery. Branch cancellation and management scope follow B04 and B10.                                          |
| F33 Child extension tools        | Give two researchers the project's web tools; clear the parent's retained content and cancel one child's request.                                                    | Needed tools are independently initialized under each child's allowlist. Parent clearing and one child's cancellation do not erase or cancel another session's retained content/work. Third-party global-state isolation needs separate implementation evidence. |

## Boundary scenarios

| Scenario                          | Actual operation and required observation                                                                                                                                                                                                                                                                                                                                                                                                                           | Design rules                     |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| B01 Dispatch admission            | Submit a dependency cycle, a nonexistent dependency, a missing role and an invalid tool selection in separate trials. Each invalid dispatch starts no tasks and consumes no cumulative allowance. Repeat at the depth and cumulative limits; a valid task with no concurrent slot queues instead.                                                                                                                                                                   | Q18, Q24, Q26, Q28, Q50          |
| B02 Waiting and quotas            | Fill two configured execution slots with leads that delegate and wait. Their children must run; resuming leads rejoin the queue. Add another top-level dispatch to check shared main-session concurrency and separate cumulative allowances. Follow-ups count against the relevant allowance.                                                                                                                                                                       | Q15, Q21, Q24, Q26               |
| B03 Failure and queued work       | Fail investigation A before dependent B starts while unrelated C runs. B ends skipped with its reason, C continues. Explicit repair produces a new result; old B is not automatically rerun. Queue a follow-up behind a successful task and verify it starts afterward without overlapping the same subagent. Separately fail/cancel/time out a subagent with remaining queued work: the caller must continue or cancel the queue.                                  | Q14, Q20, Q22-Q23, Q29, Q32, Q56 |
| B04 Cancellation timing           | Cancel during queueing, initialization, an active tool and an explicit child wait. No cancelled branch may start new descendants or regain running status after cancellation settles. A tool that delays stopping keeps the task cancelling and occupies its active slot; the next assignment and cleanup wait. Preserve unsaved partial work. Repeat cancellation for an entire dispatch containing independent top-level tasks.                                   | Q17, Q36, Q47                    |
| B05 Three different timeouts      | Expire a result wait while its child continues; expire an unanswered question while independent work remains possible; exhaust execution time while descendants still run. Verify each distinct outcome, excluded queue/wait time, configurable values and recorded reasons.                                                                                                                                                                                        | Q27, Q40, Q46, Q48               |
| B06 Message timing and scope      | Send an ordinary message during a tool call, steer during that turn, and send both to an ended task. Ordinary messages are retained and delivered at the next model opportunity; ended-task messages notify the main agent without restarting work, and ended-task steering is rejected. Try peer/cross-depth addressing and cross-dispatch contact; only the main agent relays between dispatches.                                                                 | Q38-Q40, Q49                     |
| B07 Baselines and configuration   | Dispatch from tracked uncommitted edits with one explicitly selected untracked file and another unselected file. Verify the snapshot contents and unchanged original. Modify the main code and role configuration while tasks queue/run: their accepted snapshots remain stable. Explicit live-code selection and a new follow-up use their chosen inputs.                                                                                                          | Q19, Q33-Q34, Q41-Q42, Q51-Q52   |
| B08 Code handoff and cleanup      | Make worktree creation fail, then run successful independent writers and an explicit integration with a conflict. Setup failure must not fall back to the original directory. Inspect returned artifacts before explicitly applying them. Reclaim saved inactive worktrees, keep branches/records, and refuse automatic removal when unsaved changes remain. Repeat non-Git writing only with explicit selection.                                                   | Q30-Q31, Q35-Q37                 |
| B09 Session and artifact recovery | Normally switch/exit with running children, then reopen; separately interrupt Pi after task creation, a state transition and result delivery before batch settlement. Inspect restored records and explicit continuation. Try a missing worktree with an available commit, a missing original commit, missing context and one corrupt record among usable records. Restore what is available, report each gap and never silently substitute a new session/baseline. | Q25, Q44, Q53, Q57               |
| B10 Tool and management authority | Let a read-only researcher request write tools for a descendant; let a peer try cancellation, steering and follow-up outside its descendant branch. Reject those operations without affecting the target. An authorized ancestor can arrange the work within its own scope. Inspect default read-only tools and per-child extension state; tool allowlists alone are not evidence of an operating-system sandbox.                                                   | Q18, Q45, Q58-Q59                |
| B11 Final delivery and meaning    | Have a lead return early, then let a child deliver a new finding. The lead waits without occupying a slot and consolidates within the same task before final delivery. Compare a successful failure-reproduction investigation with an unsuccessful repair: only the fulfilled assignment releases dependents; code acceptance and test evidence remain separately inspectable.                                                                                     | Q16, Q23, Q55, Q60               |
| B12 Evidence and result retention | Deliver a long report, continue the same reviewer, record provider retries/usage, and trigger a failing lifecycle listener. Read full old/new reports, compare per-task and aggregate measurements, and verify that listener errors do not change outcomes. Check copied-history content and independent child web caches as well as task records.                                                                                                                  | Q14, Q19, Q35, Q43, Q45, Q54     |

## Confirmation and remaining implementation work

The maintainer has accepted the behavioral decisions through Q60. Confirmation of this scenario coverage and shared understanding is still pending. After that confirmation, the agreed next stage is independent UI design; UI exploration may reopen a behavior decision when a concrete scenario requires it.

Tool names and schemas, source layout, scheduler/session adapters, storage format, extension isolation and process-stop mechanisms still need implementation design and evidence. This specification does not claim those mechanisms exist or that arbitrary third-party state and external side effects can already be isolated or reversed. Scope beyond F01-F33 remains as stated in the design record.

# Subagent acceptance scenarios

[简体中文](i18n/zh-CN/subagents-acceptance.md) · English is normative.

Status: proposed acceptance coverage for maintainer confirmation in [#64](https://github.com/jczhang02/pi-stuff/issues/64). The [design record](subagents-design.md) retains the accepted F01-F33 scope and incorporates the [source-review revisions](subagents-decision-review.md) to Q1-Q60. These revisions are proposed, not newly approved. These tables describe future operations and pass conditions; no scenario below has been executed or passed.

## How to use this specification

Run scenarios through the supported actual Pi host with isolated project, settings and session data, following [quality assurance](quality-assurance.md). A disposable development project should contain a reproducible login bug, a failing test, an independent payment task and branches that can be integrated. Use harmless fixture instructions and data for context and tool checks.

Record the tested revision, host/environment, effective configuration, operations, task identities, observed outcomes and relevant artifacts. Controlled providers can make scheduling, errors and interruption repeatable; identify that environment rather than treating it as evidence of live-provider behavior. Use configured short waits for timeout cases and separately check the documented defaults. The model-facing entry point is one `subagent` tool; verify the exposed tool list and exercise model-invoked subagent operations through its commands. UI presentation and exact command names and parameters remain open.

Every F row needs evidence. Boundary scenarios B01-B12 supplement those rows; one combined development workflow cannot replace separate parallel, serial or dependency-graph coverage. Missing environments or evidence remain unverified. The tables are requirements for later verification, not instructions to execute product code during this design discussion.

## Execution and task control

| Capability                      | Actual use                                                                                                                                | Pass condition                                                                                                                                                                                                                                             |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F01 Single delegation           | Ask one researcher to locate the login failure without copying parent history.                                                            | It has its own context and task record; intermediate work stays in its session, and its final result is available to the parent.                                                                                                                           |
| F02 Parallel execution          | Dispatch login and payment investigations together with two available slots.                                                              | Both make progress during overlapping execution periods, retain separate results and stay within the concurrency limit.                                                                                                                                    |
| F03 Serial execution            | Dispatch investigation, repair and review as a chain.                                                                                     | Each task starts only after its predecessor completes; the next task receives the required report and code artifact.                                                                                                                                       |
| F04 Dependency graph            | Let API implementation depend on a short API investigation, while integration depends on both API and a longer database branch.           | API work starts when its own dependency and a slot are ready; integration waits for both inputs. Invalid graphs and failed dependencies follow B01 and B03.                                                                                                |
| F05 Upstream results            | Give an implementer a long research report and its file/commit references.                                                                | It receives the final report and references, not the whole process log by default. Above the configured length, a marked preview points to readable complete output.                                                                                       |
| F06 Background and foreground   | Dispatch once in the background and once with a result wait; let the main agent finish a response while the background task runs.         | Background dispatch returns a usable identity before completion. The wait observes the task, and ending the main response does not stop its top-level background dispatch. A child dispatching in the background still owns and must join its descendants. |
| F07 Status and results          | Query a dispatch and its tasks while queued, executing, waiting, cancelling and ended, then read an earlier result after follow-up.       | Queries distinguish execution state, declared assignment outcome and main-agent acceptance, identify task/agent ownership, and preserve fixed old result references after follow-up.                                                                       |
| F08 Bounded waits               | Wait for a slow researcher with a short configured wait, then wait again.                                                                 | Wait expiry returns current state while the child continues. Completion, questions and failures wake relevant waits. The configurable sixty-second trial value is a single wait bound, not an automatic polling interval.                                  |
| F09 Notifications               | Let one researcher complete and another fail while the main agent does other work.                                                        | The parent receives correctly associated completion/failure notifications and can retrieve the matching records; failure is reported without waiting for unrelated work to finish. Dispatch settlement is reported after all its tasks have ended.         |
| F10 Cancellation                | Cancel a backend lead with active database and API descendants.                                                                           | The entire branch stops accepting new descendants; execution stops before cancellation settles or workspaces are reclaimed. Existing records and code remain inspectable. See B04.                                                                         |
| F11 Failed/aborted continuation | Fail a repair after it has changed a file, then explicitly continue with the same subagent; repeat with cancellation in a separate trial. | Its available context and partial artifact are used, with a new assignment record and the old outcome retained. No unrelated old graph nodes automatically restart. See B03 and B09.                                                                       |
| F12 Steering                    | During a tool call, tell an implementer to prioritize login and defer payment; separately steer all running children in a dispatch.       | Steering is processed after the current turn's tools and before the next model call, within the same task. Steering an ended task is explicitly rejected.                                                                                                  |

## Communication and configuration

| Capability                   | Actual use                                                                                                                                   | Pass condition                                                                                                                                                                                                                                                                                                     |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| F13 Ask the parent           | A database child asks its direct parent to clarify a field; run answered, unanswered and late-reply variants.                                | Waiting releases the execution slot only after other active execution ends, as in B02. A timely reply resumes work through the queue; expiry reports no answer without inventing one or automatically failing the whole task. Default answer wait is ten minutes. A late reply stays associated with the question. |
| F14 Report a finding         | A researcher reports the likely faulty file, then continues investigating.                                                                   | The parent can read the finding while the child continues without waiting for a reply.                                                                                                                                                                                                                             |
| F15 Agent mailbox            | A database agent sends a field convention to an API agent at another depth in the same dispatch.                                             | Known-ID delivery respects the dispatch boundary; the recipient receives it before its next model processing step. Ended-task and message-scope variants are in B06; management authority is checked in B10.                                                                                                       |
| F16 Inline roles             | Define a temporary release-note investigator with task-specific instructions and limited tools.                                              | The child uses that definition without requiring a role file and stays within the inherited tool ceiling.                                                                                                                                                                                                          |
| F17 Role files               | Discover project and user role files, select a reviewer explicitly, then dispatch without specifying a role.                                 | The selected role is used; the unspecified case uses a generic role. Mentioning a database does not silently select or switch roles.                                                                                                                                                                               |
| F18 Model and thinking       | Set differing model/thinking values in the call, role, project, user and parent configuration, then remove higher-priority settings in turn. | New agents follow Q42 precedence. Queued tasks and retained-agent follow-ups keep saved values despite role-file edits. Explicit supported overrides are recorded and effective ceilings still apply; newly created agents use the changed role.                                                                   |
| F19 Tool selection           | Assign a read-only researcher, a writable implementer and a child requesting tools its parent lacks.                                         | Tool exposure and effective execution permissions stay within parent ceilings. Tighten an inherited restriction before a follow-up and verify it cannot be bypassed by saved configuration. Default read-only roles have no arbitrary shell or write-capable extensions. See B10.                                  |
| F20 Working directory        | Dispatch into the API subdirectory, then explicitly choose a non-Git document folder for a write task.                                       | Relative work uses the intended location within the selected baseline. Non-Git direct writing requires explicit selection; it is not a fallback from failed isolation.                                                                                                                                             |
| F21 Project rules and skills | Place a harmless project instruction and a relevant configured skill in the selected project, then delegate matching work.                   | The child's resource loading uses the intended working directory, and its context/work demonstrates access to those instructions and skill. Loading a skill alone does not grant an extension tool.                                                                                                                |

## Limits, code and records

| Capability                  | Actual use                                                                                                                                      | Pass condition                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F22 Resource limits         | Dispatch enough researchers across two top-level dispatches to fill the main session, then create descendants and follow-ups near their limits. | Configurable trial values are eight execution slots per main session, sixty-four accepted tasks per dispatch and depth three from main at zero. Waiting/context retention does not refund cumulative count or depth. Follow-ups charge the original dispatch, provider retries do not create tasks. Use small limits to verify B01-B02; record resource costs without claiming calibrated defaults. |
| F23 Execution timeout       | Let an implementation task use a short configured execution allowance, including a tool call and explicit waiting phases.                       | Only Q27 execution stages consume a configured deadline. Expiry requests branch cancellation, retains artifacts/cause and obeys actual-stop rules without rerun. An unconfigured task has no cumulative execution deadline. Tool/provider timeouts remain separate. See B05.                                                                                                                        |
| F24 Provider retry          | Cause a retryable provider/network response, then separately cause a failed code test.                                                          | Provider requests follow Pi's configured retry behavior within the same task. A failed test or arbitrary failed assignment does not automatically rerun as a new task.                                                                                                                                                                                                                              |
| F25 Usage accounting        | Run a lead, two descendants and a later follow-up, including a provider retry.                                                                  | Per-task input/output/cache tokens, cost and turns are inspectable where available; aggregate totals do not double-count descendants or overwrite earlier tasks. Missing provider measurements are identified rather than invented. No hard token/cost budget is claimed.                                                                                                                           |
| F26 Worktree management     | Dispatch two writers from a dirty Git workspace, collect their code and allow eligible worktrees to be reclaimed.                               | Independent writers have separate worktrees; each retained agent reuses its workspace across assignments. Fixed commits/diffs/checks are returned for explicit application, leaving the original unchanged. Explicit workspace release and content preservation precede automatic cleanup. See B07-B08.                                                                                             |
| F27 Branch inheritance      | Run a repair followed by review; separately combine two write branches through an integration task.                                             | A single-input task consumes a fixed upstream commit. Multiple code artifacts are explicitly integrated, including conflicts. Advancing the original branch in a later follow-up cannot silently alter already accepted downstream input.                                                                                                                                                           |
| F28 Persistence and restore | Close or interrupt the main session during a batch, reopen it and inspect completed and unfinished tasks.                                       | Usable records, contexts and fixed artifacts restore; unfinished work is interrupted and needs explicit continuation, without replaying writes. Terminal durability is distinguished from notification and optional listener errors. Missing state and unknown external activity follow B09.                                                                                                        |
| F29 Lifecycle events        | Observe task lifecycle events from an extension, then make its listener throw.                                                                  | Optional observer failures are recorded without changing outcomes or stalling scheduling. A required persistence/artifact-save failure remains a core error, and must not be hidden behind the observer rule.                                                                                                                                                                                       |

## Added capabilities

| Capability                       | Actual use                                                                                                                                                           | Pass condition                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F30 Completed-subagent follow-up | Ask the same reviewer to re-review a revised artifact, both before and after reopening the main session.                                                             | Logical identity/recoverable history and workspace continue, including after unloading and recreating a live runtime; each assignment keeps its own record and fixed result. A write follow-up reuses a retained workspace unless a baseline change is explicit; a released or missing workspace follows Q53 recovery or explicit failure. Earlier parent tasks and consumers stay settled. Recovery or alternate baselines never silently discard partial work. |
| F31 Parent-history copy          | Dispatch one child with a fresh context and another with copied history containing tool results and a compaction summary; send the parent new information afterward. | Copy completed visible history and existing summaries at a valid fork boundary. Include a dispatch with pending tool calls: the child request must remain valid and any fork-control records clearly identified. No live handles, permissions, workspace mutations or later parent messages are copied implicitly.                                                                                                                                               |
| F32 Recursive delegation         | A backend lead creates database and API children; one returns late, one fails, and one attempts to delegate beyond its limits.                                       | Shared quotas/depth/permissions hold; safe waiting releases slots. The lead joins tasks it delegated and incorporates unconsumed child outcomes. A later assignment to a retained descendant does not reopen the old parent. No redundant model turn is required after an already completed explicit join. See B04/B10/B11.                                                                                                                                      |
| F33 Child extension tools        | Give two researchers the project's web tools; clear the parent's retained content and cancel one child's request.                                                    | Selected extension entrypoints are initialized for the child and tool exposure is filtered. Parent cache clearing and one child cancellation do not affect another session. Test a multi-tool entrypoint and factory hooks to demonstrate filtering is not prevention of initialization side effects. Unsupported/global-state-unsafe entries fail explicitly; no universal isolation claim.                                                                     |

## Boundary scenarios

| Scenario                          | Actual operation and required observation                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Design rules                     |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| B01 Dispatch admission            | Reject invalid graph/role/tool/depth/count inputs before task creation or quota consumption. Concurrent valid admissions cannot overbook cumulative allowance; execution-slot shortage only queues. After valid admission, make one worktree initialization fail: record its startup failure, retain accepted counts and let unrelated started work continue.                                                                                                                                | Q18, Q24, Q26, Q28, Q50          |
| B02 Waiting and quotas            | With two execution slots, let two leads delegate and wait; children run and leads reacquire slots on resume. Keep another tool active during a wait and verify the slot is not released early. Retained contexts do not occupy execution slots; neither waiting nor new follow-up calls reset original dispatch counts or depth. Check shared concurrency across dispatches.                                                                                                                 | Q15, Q21, Q24, Q26               |
| B03 Failure and queued work       | Fail A before dependent B starts; B ends skipped while unrelated C continues. Explicit repair creates a new result without rerunning old B. Successful assignments advance the same-agent queue without overlap. Abnormal outcomes hold remaining uncancelled work; an authorized caller can explicitly run recovery before releasing that queue. Ordinary messages do not release it. Recovery may release independent uncancelled entries, never queued tasks owned by a cancelled branch. | Q14, Q20, Q22-Q23, Q29, Q32, Q56 |
| B04 Cancellation timing           | Cancel during queueing, initialization, an active tool and an explicit child wait. No cancelled branch may start new descendants or regain running status after cancellation settles. A tool that delays stopping keeps the task cancelling and occupies its active slot; the next assignment and cleanup wait. Preserve unsaved partial work. Repeat cancellation for an entire dispatch containing independent top-level tasks.                                                            | Q17, Q36, Q47                    |
| B05 Three different timeouts      | Expire a result wait while children continue; expire an answer wait with independent work available; expire a configured execution deadline while descendants run. Check distinct outcomes, exclusions, actual-stop acknowledgement and no automatic rerun. An unconfigured task has no cumulative deadline; repeated unchanged waits are not an automatic wakeup policy.                                                                                                                    | Q27, Q40, Q46, Q48               |
| B06 Message timing and scope      | Message and steer during a tool call, then target an ended task. Distinguish stored receipt from model consumption. Ended-task messages notify main without restarting; steering is rejected. Test peer/cross-depth addressing and cross-dispatch relay. Explicit follow-up is separately authorized and creates a new record, unlike ordinary message delivery.                                                                                                                             | Q38-Q40, Q49                     |
| B07 Baselines and configuration   | Capture tracked dirty changes and one selected untracked file while leaving the original index/worktree unchanged. Mutate the source during capture: retry or fail, never silently mix revisions. After acceptance, edit source and role files; code inputs and saved configuration stay stable. Follow-up reuses workspace/configuration; explicit baseline/model changes are recorded. Test a fork with pending tool calls and explicit live-code selection.                               | Q19, Q33-Q34, Q41-Q42, Q51-Q52   |
| B08 Code handoff and cleanup      | Fail isolation setup with no original-directory fallback. Run independent writers and explicit integration with conflicts; consume fixed commits, not moving tips. Retain an idle workspace for follow-up. After explicit release, clean only when all content is preserved; test untracked/ignored artifacts and a running process. Non-Git direct writing remains explicit. Advance an old branch and verify old results remain unchanged.                                                 | Q30-Q31, Q35-Q37                 |
| B09 Session and artifact recovery | Switch/exit the actual Pi session with children, then reopen; response endings and UI focus changes do not stop them. Interrupt after creation, transitions and result persistence; keep usable records and report gaps. Test missing worktree with saved commit, unsaved content, missing context/commit, corrupt records and unknown external activity. Rebind the restored session, require explicit continuation and never substitute parent cwd.                                        | Q25, Q44, Q53, Q57               |
| B10 Tool and management authority | Reject a read-only parent delegating wider tools/permissions, and peer cancellation/steering/follow-up outside ownership. Tighten inherited permissions before follow-up: saved configuration cannot restore the old grant. Inspect separate extension initialization, multi-tool factories, shared globals and cache cancellation. Tool names, a worktree cwd and copied history are not evidence of an OS sandbox.                                                                         | Q18, Q45, Q58-Q59                |
| B11 Final delivery and meaning    | Let a lead report before a late child finding: join and consume it within the same task. Also test an explicit completed join without an extra summary turn. Give a retained child a later assignment; the old parent stays settled. Compare normal execution with an explicit inability report, missing declaration and a fulfilled reproduction report. Only the settled fulfilled declaration releases dependencies; a wrong fulfillment claim can still fail main-agent acceptance.      | Q16, Q23, Q55, Q60               |
| B12 Evidence and result retention | Read full long reports and fixed old/new artifacts after follow-up. Check retry/usage totals without double counting. An optional observer failure leaves outcomes intact; a core result/artifact-store failure is surfaced, never reported as durable success, and cannot release consumers even with a fulfilled declaration. Verify notification/result ordering, fork history and independent child web caches.                                                                          | Q14, Q19, Q35, Q43, Q45, Q54     |

## Confirmation and remaining implementation work

The maintainer accepted the interview answers through Q60 and then requested source review before UI. These scenarios now follow the consolidated review proposal, including revised workspace/configuration lifetime and execution deadlines. Overall confirmation remains pending; source inspection has not executed these acceptance scenarios.

Tool names and schemas, source layout, scheduler/session adapters, storage format, extension isolation and process-stop mechanisms still need implementation design and evidence. This specification does not claim those mechanisms exist or that arbitrary third-party state and external side effects can already be isolated or reversed. Scope beyond F01-F33 remains as stated in the design record.
